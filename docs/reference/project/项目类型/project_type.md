# AI开发模式配置模板（Spec/Vibe/Human Gate）

**版本**：v1.1  
**创建日期**：2026-01-15  
**维护者**：[henrypt]  
**说明**：本模板用于标准化不同类型项目的AI开发模式配置，所有项目必须基于此模板选择对应的开发策略。

---

## 一、全局核心配置（所有项目通用）

### 1.1 核心匹配原则

- ✅ **风险越高、确定性要求越强** → 越偏向 **Spec Coding**
- ✅ **需求越模糊、探索性越强** → 越偏向 **Vibe Coding**
- ✅ **所有项目都需要 Human Gate**，仅严格程度不同
- ✅ **绝大多数项目采用混合模式**，单一模式极少适用

### 1.2 完整项目类型与开发模式对照表

| 项目类型 | 核心特点 | 推荐开发模式 | Human Gate严格程度 | 关键注意事项 |
|---------|---------|-------------|-------------------|-------------|
| **从0到1创新型新项目** | 业务需求高度不确定，允许试错，速度优先 | **前期：100% Vibe<br>中期：70% Vibe + 30% Spec<br>后期：转为Spec为主** | 极宽松 → 标准 | 前期只关注"是否解决问题"，不纠结代码质量；验证通过后必须用Spec重构 |
| **从0到1稳定型新项目** | 业务需求明确稳定，但技术栈全新，技术不确定性高 | **技术验证：100% Vibe<br>架构设计：100% Spec<br>业务开发：70% Spec + 30% Vibe** | 标准 → 极其严格 | 先技术验证再架构设计，业务层Spec技术层Vibe |
| **成熟型新项目** | 需求明确，有清晰的业务目标和验收标准，有参考案例 | **90% Spec + 10% Vibe** | 标准 → 严格 | 先写完整架构Spec和核心模块Spec，再分模块开发；允许AI在实现细节上自由发挥 |
| **核心系统大升级** | 风险极高，影响范围广，需要严格的兼容性保障，多人并行开发 | **核心层：100% Spec<br>功能层：70% Spec + 30% Vibe<br>创新层：100% Vibe** | 分级严格<br>（核心模块100%覆盖，资深架构师审查） | 任何核心接口和数据结构变更必须先改Spec；严禁在核心层使用Vibe模式 |
| **常规功能迭代** | 需求相对明确，影响范围小，交付周期短 | **70% Spec + 30% Vibe** | 标准 | 编写轻量级Spec，明确输入输出和验收标准；小的UI调整可以直接用Vibe |
| **普通Bug修复** | 问题明确，影响范围小，修复难度低 | **100% Vibe** | 宽松 | 快速修复，快速验证；修复后更新相关文档 |
| **严重/生产级Bug修复** | 影响范围大，可能导致系统崩溃或数据丢失 | **先Vibe紧急止血<br>事后用Spec彻底重构** | 严格 → 极其严格 | 紧急修复后必须进行全面回归测试；事后用Spec模式重新设计解决方案 |
| **技术债务清理/代码重构** | 不改变功能，只优化代码质量和架构，需要保证不破坏现有功能 | **90% Spec + 10% Vibe** | 严格 | 先编写原有功能的Spec作为验收标准；重构后必须通过所有原有测试 |
| **原型验证/概念演示** | 只关注是否能展示效果，不考虑可维护性和性能 | **100% Vibe** | 极宽松 | 追求速度，允许"脏代码"；原型代码绝对不能直接用于生产 |
| **线上紧急故障处理** | 时间极其紧迫，需要立即恢复服务 | **先Vibe快速解决<br>事后用Spec复盘和优化** | 快速审查 | 优先恢复服务，再排查根本原因；事后必须更新Spec和应急预案 |
| **内部工具/脚本开发** | 需求灵活，使用范围小，维护成本低 | **80% Vibe + 20% Spec** | 极宽松 → 宽松 | 可以快速迭代；如果工具变得重要，再转为Spec模式 |
| **第三方系统集成** | 接口规范明确，需要严格遵守第三方协议，错误处理复杂 | **95% Spec + 5% Vibe** | 严格 | 必须详细编写接口调用、错误处理和数据转换的Spec；重点测试边界情况 |
| **数据迁移/同步** | 数据正确性至关重要，一旦出错后果严重 | **100% Spec** | 极其严格（多人交叉审查） | 编写详细的数据映射、转换规则和校验逻辑Spec；必须进行全量数据验证 |
| **安全加固/合规改造** | 要求零疏漏，必须符合相关法规和标准 | **100% Spec** | 极其严格（安全专家参与审查） | 所有安全措施必须在Spec中明确规定；严禁任何未经审查的代码变更 |
| **性能优化** | 目标明确（如响应时间、吞吐量），需要量化指标 | **前期：Vibe探索方案<br>后期：Spec实现最优解** | 标准 → 严格 | 先用Vibe快速尝试多种优化方案；确定最优方案后用Spec模式实现 |

### 1.3 通用Human Gate分级标准

| 等级 | 严格程度 | 审查覆盖率 | 审查人员 | 审查内容 | 合并条件 |
|------|----------|------------|----------|----------|----------|
| L0 | 极宽松 | <30% | 普通开发者 | 功能是否正常运行 | 自测通过即可合并 |
| L1 | 宽松 | 30%-50% | 普通开发者 | 功能正确性、基本代码规范 | 代码审查通过+单元测试通过 |
| L2 | 标准 | 50%-80% | 高级开发者/模块负责人 | 业务逻辑、代码质量、可维护性 | 代码审查通过+所有测试通过 |
| L3 | 严格 | 80%-100% | 技术负责人/架构师 | 架构合理性、安全性、兼容性 | 多人交叉审查通过+全量测试通过 |
| L4 | 极其严格 | 100% | 架构师+安全专家+产品负责人 | 所有内容，包括设计文档和Spec | 全员评审通过+灰度验证通过 |

### 1.4 通用决策公式

1. **风险等级判断**：
   - 高风险（核心业务/数据安全/系统稳定性）→ Spec优先
   - 中风险（部分功能/用户体验）→ 混合模式
   - 低风险（内部使用/临时工具/原型）→ Vibe优先

2. **需求明确度判断**：
   - 需求明确（有清晰验收标准）→ Spec优先
   - 需求模糊（需要探索验证）→ Vibe优先

3. **技术成熟度判断**：
   - 技术成熟（文档完善、社区活跃、案例丰富）→ Spec优先
   - 技术不成熟（文档缺失、社区小、坑多）→ Vibe优先

4. **团队规模判断**：
   - 多人协作 → Spec优先（Spec是团队契约）
   - 单人开发 → 可适当增加Vibe比例

## 三、使用说明

1. **项目启动时**：根据项目类型，选择对应的配置块，作为项目开发的指导原则
2. **团队对齐**：项目开始前，组织团队成员学习本模板，确保所有人理解并达成共识
3. **动态调整**：在项目过程中，可以根据实际情况调整开发模式和Human Gate等级，但必须在团队内同步
4. **持续完善**：当遇到新的项目类型或发现现有配置不合理时，及时更新本模板
5. **版本管理**：每次修改模板都要更新版本号和修改记录

## 五、附录：两种从0到1项目的核心区别对比

| 维度 | 从0到1创新型新项目 | 从0到1稳定型新项目 |
|------|-------------------|-------------------|
| **不确定性来源** | 业务需求 | 技术实现 |
| **核心目标** | 验证产品价值 | 按时交付稳定产品 |
| **失败风险** | 产品没人用 | 技术做不出来 |
| **技术栈选择** | 成熟稳定 | 最新前沿 |
| **开发模式** | 业务层Vibe，技术层Spec | 业务层Spec，技术层Vibe |
| **前期重点** | 快速出原型，获取用户反馈 | 技术验证，架构设计 |
| **迭代方式** | 频繁调整方向，快速迭代 | 方向固定，稳步推进 |
| **代码质量要求** | 前期低，后期高 | 全程高 |
| **Human Gate重点** | 产品价值 | 技术质量 |
