# init.md - 项目初始化 Prompt 合集（AI 工程化版）

---

## 一、初始化 Prompt 核心价值
项目初始化是 AI 工程化开发的起点，清晰的初始化 Prompt 能让 AI 快速理解项目边界、技术栈和核心目标，避免后续开发出现方向偏差，降低重构成本。

核心原则：
- 先分析后行动
- 明确边界和限制
- 输出结构化分析结果
- 不做无意义的重构

---

## 二、通用项目初始化 Prompt（核心）
```txt
这是一个待初始化的 [项目类型/业务领域] 项目。

目标：
完成项目基础架构初始化，搭建可落地的工程化基础。

技术栈要求：
[明确技术栈，如：Vue3 + TypeScript + Vite + Pinia + Element Plus]

限制：
- 符合行业通用工程规范
- 低耦合、高内聚的模块设计
- 兼容主流浏览器（Chrome/Firefox/Safari/Edge）
- 考虑移动端适配（如有）
- 不引入冗余依赖

禁止：
- 不要过度设计
- 不要引入未验证的小众依赖
- 不要编写业务逻辑代码
- 不要忽略工程化配置

输出：
1. 项目完整目录结构
2. 核心配置文件（如package.json、vite.config.ts等）
3. 技术栈落地规范
4. 初始化风险点
5. 后续扩展建议

先分析，再输出具体方案，不直接生成完整代码。
```

## 三、项目结构分析初始化
```txt
请基于以下技术栈完成项目初始化的结构分析：
技术栈：[填写技术栈]
业务领域：[填写业务领域，如：电商后台/移动端社交应用]

分析并输出：
1. 标准化目录结构（按功能/模块划分）
2. 核心目录的职责说明
3. 配置文件的组织方式
4. 静态资源的管理方案
5. 通用工具类的规划
6. 类型定义（TypeScript）的统一管理
7. 工程化配置（ESLint/Prettier/Husky）的建议

要求：
- 结构具备可扩展性
- 符合技术栈最佳实践
- 适配后续业务迭代
```

## 四、技术栈适配初始化
```txt
目标：
为 [项目名称] 初始化技术栈适配方案。

指定技术栈：
[前端框架 + 构建工具 + 状态管理 + UI组件 + 其他核心依赖]

输出：
1. 核心依赖版本选择（兼容且稳定的版本）
2. package.json 核心配置（scripts/dependencies/devDependencies）
3. 关键配置文件（如vite.config.ts、tsconfig.json、.eslintrc.js）
4. 技术栈融合的注意事项
5. 版本兼容风险点
6. 替代方案（如有版本冲突）

限制：
- 优先选择官方推荐配置
- 依赖版本避免最新的不稳定版本
- 保持配置简洁可维护
```

## 五、工程化规范初始化
```txt
目标：
为项目初始化统一的工程化规范，保障团队协作效率。

输出规范文档包含：
1. 代码规范（命名/缩进/注释/文件命名）
2. Git 工作流规范（分支管理/Commit规范/PR规范）
3. 代码提交校验规则（ESLint/Prettier/Husky配置）
4. 开发环境配置规范（Node版本/包管理器/环境变量）
5. 构建/部署规范（开发/测试/生产环境区分）

要求：
- 规范具备可落地性
- 符合行业通用标准
- 适配指定技术栈
- 输出可直接使用的配置文件模板
```

## 六、初始化检查清单 Prompt
```txt
请基于已完成的项目初始化内容，生成完整的检查清单：

检查维度：
1. 目录结构完整性
2. 配置文件正确性
3. 依赖版本兼容性
4. 工程化规范覆盖度
5. 技术栈适配性
6. 可扩展性
7. 兼容性（浏览器/设备）
8. 安全性基础配置

输出：
1. 逐条检查项（带是否达标标识）
2. 未达标项的修复建议
3. 初始化质量评分
4. 后续优化优先级
```

## 七、初始化阶段 AI 控制 Prompt
```txt
针对项目初始化工作，需严格遵守以下规则：

1. 先输出分析方案，确认后再生成代码
2. 只生成初始化必要的基础代码，不编写业务逻辑
3. 保持配置文件的简洁性，避免过度配置
4. 不引入非必要的依赖包
5. 所有配置需附带注释说明用途
6. 输出内容需包含风险提示和替代方案
7. 严格遵循指定技术栈的最佳实践
8. 初始化结果需具备可落地性，而非理论方案
```

## 八、初始化文档生成 Prompt
```txt
请基于项目初始化方案，生成项目初始化文档：

文档包含：
1. 项目概述（技术栈/业务目标/核心价值）
2. 环境搭建步骤（本地开发环境配置）
3. 目录结构说明（核心目录/文件的职责）
4. 核心配置说明（关键配置项的作用）
5. 开发规范（代码/提交/协作）
6. 常见问题解决方案
7. 后续迭代建议

要求：
- 文档面向团队开发人员，通俗易懂
- 步骤具备可操作性
- 包含必要的示例代码
- 格式清晰，便于查阅
```

## 九、初始化最小修改原则
```txt
在项目初始化过程中，需遵循最小必要原则：

禁止：
- 不要设计过度复杂的目录结构
- 不要引入未验证的依赖
- 不要编写冗余的配置
- 不要添加无关的功能模块
- 不要修改技术栈核心默认配置（除非必要）

只做：
- 满足项目基础运行的核心配置
- 保障代码规范的基础工程化配置
- 适配业务的最小目录结构
- 必要的兼容性配置
```

## 核心思想
项目初始化的核心不是“堆砌配置”，而是“搭建适配业务、符合规范、具备扩展性的基础框架”。通过清晰的 Prompt 定义初始化任务，让 AI 输出可控、可落地、低风险的初始化方案，为后续开发奠定坚实基础。

并不是一~九的模板都“必须全部使用”，而是要根据你的**实际开发场景**和**核心诉求**来选择，其中部分是「基础必备」，部分是「场景化按需使用」，部分是「进阶推荐」。以下是分模块的必要性分析：

### 一、Prompt 的真正作用（必懂，非“用模板”而是“建认知”）
✅ **必须理解**（不是“用模板”，而是底层逻辑）
这部分不是可复用的模板，而是核心认知：Prompt 是 AI 的「任务说明书」，而非“随便问一句话”。只有理解这个核心，你写的所有 Prompt 才会更清晰、AI 输出才会更可控。
**什么时候用**：写任何 Prompt 前，先提醒自己“要把任务说清楚”，是所有后续模板的思想基础。

### 二、AI 工程化 Prompt 核心原则（必用，所有场景的骨架）
✅ **必须用**（核心公式是所有 Prompt 的底层框架）
`背景+目标+限制+禁止事项+输出要求` 这个公式，是你写任何 Prompt 都该遵循的结构——哪怕不用完整模板，也必须覆盖这5个维度，否则 AI 容易输出失控、偏离需求。
**什么时候用**：写任何 Prompt（开发/修Bug/重构）时，都要按这个公式组织内容。

### 三、万能工程 Prompt（必用，通用兜底模板）
✅ **必须用**（覆盖80%的日常开发场景）
这是“通用款”模板，不管是做功能开发、改Bug、小优化，都可以基于这个模板调整——它能保证 AI 先分析、再输出，且输出内容结构化（方案/文件/风险/原因），避免 AI 直接乱写代码。
**什么时候用**：不确定用哪个细分模板时，先用这个兜底。

### 四、项目分析 Prompt（按需，仅项目初始化/接手新项目用）
⭕ **按需使用**
只有在「项目初始化、接手陌生项目、梳理项目架构」时需要（比如用 Cursor/Claude 读整个项目、输出项目地图）；日常改一个小功能、修一个 Bug 时完全用不上。
**什么时候用**：刚接手项目、需要快速理清技术栈/目录结构/核心模块时。

### 五、功能开发 Prompt（按需，仅功能开发场景用）
⭕ **按需使用**
细分了“新页面/新组件/API 开发”模板，只有你明确要做「功能开发」时才需要；修Bug、重构、Code Review 时用不上。
**什么时候用**：需要新增页面/组件/API 模块时，直接套对应子模板即可。

### 六、Bug 修复 Prompt（必用，所有 Bug 场景的核心）
✅ **必须用**
几乎所有开发都会遇到 Bug，而“报错了帮我修”这种模糊指令是无效的——这个模板要求你说清「问题+现象+复现步骤+怀疑点」，能让 AI 精准分析根因，而非瞎猜。
**什么时候用**：任何需要 AI 排查/修复 Bug 的场景，这是唯一该用的模板（替代模糊的“帮我修bug”）。

### 七、最小修改 Prompt（必用，防 AI 失控的关键）
✅ **必须用**（所有修改场景都要加这个约束）
AI 最危险的行为是“顺手重构无关代码”，这个模板是「防失控神器」——哪怕用其他模板（比如功能开发/修Bug），也建议把这部分的“禁止项”（不重构/不改命名/不新增依赖）加进去。
**什么时候用**：任何需要 AI 修改代码的场景（开发/修Bug/小优化），都要叠加这个约束。

### 八、重构 Prompt（进阶，仅重构场景用）
⭕ **进阶按需**
只有你明确要做「模块拆分、代码重构、技术债清理」时需要；日常小修改、修Bug 时完全用不上（新手甚至可以暂时不用）。
**什么时候用**：重构前需要 AI 输出方案/风险/回滚策略时，避免重构引入新问题。

### 九、代码 Review Prompt（推荐，非必须但强烈建议）
⭐ **推荐用（进阶但高价值）**
不是“必须用”，但 AI 生成代码后，用这个模板做 Review 能大幅降低风险（比如检查空值/性能/安全问题）；如果是小项目/临时脚本，可省略；如果是生产环境代码，强烈建议用。
**什么时候用**：AI 写完代码后，需要自检/校验代码质量时。

### 最终总结：
| 类型         | 模块                | 必要性       | 核心使用场景                     |
|--------------|---------------------|--------------|----------------------------------|
| 基础必备     | 一（认知）、二（公式）、三（万能）、六（Bug）、七（最小修改） | 必须懂/必须用 | 日常开发、修Bug、小优化（80%场景） |
| 场景化按需   | 四（项目分析）、五（功能开发）| 按需         | 项目初始化、新增功能时           |
| 进阶推荐     | 八（重构）、九（Code Review）| 推荐（非必须） | 重构、生产环境代码校验时         |

简单说：**先把“一、二、三、六、七”用熟**，覆盖日常绝大部分场景；四、五、八、九根据具体需求补充即可。
