# T4核心系统升级 - 架构设计规范（经济模型v2升级专项）

## 文档说明

本文档基于T4核心系统升级的并行开发模式（立项后半段启动PRD基础 → Phase 0 PRD精细化+架构设计并行 → 开发）编制，明确T4模式下架构设计的流程、约束、交付物、审查标准，是Phase 0 L4 Human Gate审查的核心依据之一。

---

## 一、T4架构设计核心逻辑

### 1.1 T4 vs 传统T1/T2项目架构设计差异

| 维度 | T1/T2新项目（串行模式）| T4核心系统升级（并行模式）|
|--------------|---------------------------------------|---------------------------------------|
| 设计前置条件 | 立项→PRD完成后启动 | 立项约束确定后，与PRD精细化、资产复用并行启动 |
| 核心输入 | 全新PRD（无历史参考）| 立项约束+ v1 Spec（90%需求已验证）|
| 设计目标 | 探索新方案，匹配未知需求 | 固化已有规则，满足兼容性/风险控制约束 |
| 关键依赖 | PRD全量输出 | 资产复用分析结果、立项红线（双写/回滚） |
| 审查节点 | PRD审查后单独审查 | Phase 0 L4审查（与PRD/迁移方案同步）|

### 1.2 T4架构设计核心原则

1. **约束先行**：所有架构决策必须符合立项文档中不可突破的约束（100%兼容、双写、回滚、技术栈限制）；
2. **复用优先**：基于v1资产复用分析结果，最大化复用可复用资产，减少重构范围；
3. **并行协同**：与PRD精细化（固化v1 Spec）、资产复用分析同步推进，三者互相验证；
4. **风险前置**：在Phase 0完成双写、回滚、数据迁移等核心风险点的方案设计与演练。

### 1.3 架构设计嵌入执行方式

架构设计需基于立项约束 + PRD，而非单独前置。核心执行方式：

1. **Phase 0 嵌入执行**（立项 + PRD 同步）：
   - 先完成「兼容性架构设计」（数据迁移方案、双写机制、回滚预案）
   - 对应 Human Gate L4 审查重点

2. **架构分层设计**：
   - **100% Spec 模块**：公式引擎、数据兼容层 → 需明确「一致性验证标准」
   - **混合模式模块**：Yjs 协作、RAG 助手 → 需明确「灵活性边界」

3. **关联 AI 角色协同**：
   - Backend Agent / Frontend Agent / Fullstack Agent 参与架构拆解
   - DBA Agent 参与数据迁移架构设计
   - Yjs 协作层技术落地、Supabase 后端适配由对应 Agent 负责

## 三、T4架构设计核心交付物（Phase 0 L4审查必备）

### 3.1 必须提交的交付物清单

| 交付物名称 | 提交人 | 审查标准 |
|--------------------------|--------------|--------------------------------------------------------------------------|
| 《系统架构设计文档》| 架构师 | 1. 符合所有立项约束；2. 覆盖100%v1核心功能；3. 风险方案可落地 |
| 《v1资产复用分析报告》| 架构师+开发 | 1. 全量梳理v1资产；2. 明确复用/重构/放弃范围；3. 复用方案可执行 |
| 《数据迁移方案》| 架构师+DBA | 1. 覆盖全量v1数据；2. 一致性验证方法明确；3. 失败回滚预案完善 |
| 《双写与回滚预案》| 架构师+运维 | 1. 回滚流程≤30分钟；2. 双写校验规则清晰；3. 异常处理逻辑完整 |
| 《架构风险评估报告》| 技术负责人 | 1. 识别所有核心风险；2. 应对措施可落地；3. 风险影响范围可控 |
| 方案演练记录 | 测试+运维 | 1. 回滚/迁移演练完成；2. 演练结果符合验收标准；3. 问题整改完成 |

### 3.2 交付物核心要求

1. **量化指标**：所有交付物必须包含可量化的验收标准（如回滚≤30分钟、计算误差<0.0001%）；
2. **约束对齐**：明确标注每个方案点对应的立项约束条款，确保无偏离；
3. **可执行性**：包含具体的操作步骤、工具、责任人、时间节点，可直接落地；
4. **兼容性验证**：所有方案必须通过v1测试环境验证，输出验证报告。

## 四、T4架构设计L4 Human Gate审查标准

### 4.1 审查维度与通过标准

| 审查维度 | 审查内容 | 通过标准 |
|------------------|--------------------------------------------------------------------------|--------------------------------------------------------------------------|
| 约束符合性 | 架构是否符合立项文档中的核心约束（兼容/双写/回滚/技术栈）| 100%符合，无任何突破红线的设计，偏离项需有三方审批（负责人+业务+技术委员会） |
| 复用充分性 | 资产复用是否最大化，重构范围是否合理 | 可复用资产复用率≥90%，重构部分有明确的风险/收益分析 |
| 风险可控性 | 双写/回滚/迁移等核心风险的方案是否完善 | 所有核心风险已识别，方案经过演练验证，回滚/异常处理流程可落地 |
| 兼容性保障 | 公式计算、数据格式、业务逻辑是否100%兼容v1 | 有自动化校验报告，1000+测试用例通过率100%，误差符合要求 |
| 交付物完整性 | 是否提交所有必备交付物，内容是否完整 | 交付物无缺失，关键信息（步骤/指标/责任人）无遗漏 |

### 4.2 审查未通过的整改规则

1. 核心约束偏离：必须修改架构方案，重新对齐立项约束，整改后重新审查；
2. 风险方案不完善：补充方案设计，完成演练验证，提交补充报告；
3. 交付物不完整：24小时内补充缺失内容，重新提交审查；
4. 兼容性验证不充分：增加测试用例，重新执行全量校验，提交新的校验报告。

## 五、核心模块技术设计

### 5.1 架构分层

```
┌─────────────────────────────────────────────────────────┐
│ 前端层（Frontend）                                      │
│ - 界面层：兼容v1 UI布局/交互，基于Vue3重构               │
│ - 公式引擎层：HyperFormula集成，兼容v1所有财务函数         │
│ - 协作层：Yjs多人实时协作模块（Phase 2）                  │
├─────────────────────────────────────────────────────────┤
│ 接口层（API Gateway）                                   │
│ - 兼容v1所有接口格式/参数/返回值                         │
│ - 双写路由：同时转发请求至v1/v2，保证数据双写             │
│ - 灰度流量控制：按比例分流请求至v1/v2                    │
├─────────────────────────────────────────────────────────┤
│ 后端层（Backend）                                       │
│ - 核心业务层：复用v1业务逻辑Spec，基于Supabase重构        │
│ - 数据访问层：兼容v1数据库结构，支持双写/回滚数据同步       │
│ - 状态机层：版本管理模块，与v1状态流转逻辑一致             │
├─────────────────────────────────────────────────────────┤
│ 数据层（Data Layer）                                    │
│ - 主数据库：兼容v1结构，支持全量/增量数据迁移              │
│ - 备份库：v1数据镜像，用于回滚/对比验证                  │
│ - 缓存层：提升协作场景下的数据同步性能（Phase 2）         │
├─────────────────────────────────────────────────────────┤
│ 运维层（Ops）                                           │
│ - CI/CD流水线：自动化构建/测试/部署                      │
│ - 监控告警：全链路监控、双写一致性校验、性能监控           │
│ - 回滚工具：一键回滚脚本、数据恢复工具                   │
└─────────────────────────────────────────────────────────┘
```

### 5.2 核心技术栈

| 分层 | 核心技术/工具 | 说明 |
|------------|----------------------------------------|---------------------------------------|
| 前端层 | Vue3、HyperFormula、Yjs | 兼容v1交互，替换公式引擎，新增协作能力 |
| 接口层 | Nginx/网关中间件 | 实现流量灰度、双写路由 |
| 后端层 | Supabase、Node.js（复用v1核心逻辑）| 重构后端，兼容v1业务规则 |
| 数据层 | PostgreSQL（兼容v1库结构）、备份工具 | 保证数据格式/存储兼容 |
| 运维层 | Jenkins/GitLab CI、Prometheus/Grafana | 自动化部署+全链路监控 |

### 5.3 公式引擎迁移模块（Phase 1核心）

#### 5.3.1 设计目标

1. 100%兼容v1所有财务函数、计算公式；
2. 计算结果与v1误差<0.0001%；
3. 计算性能满足：100个公式计算时间<100ms。

#### 5.3.2 实现方案

1. **函数映射**：梳理v1所有自定义财务函数，在HyperFormula中实现等价映射，输出《函数映射对照表》；
2. **计算逻辑对齐**：基于v1 Spec，固化公式计算顺序、精度处理、空值/异常值处理逻辑，与v1完全一致；
3. **一致性校验**：开发自动化校验工具，批量执行1000+测试用例，对比v1/v2计算结果；
4. **性能优化**：对高频计算场景做缓存优化，避免重复计算。

### 5.4 双写与回滚模块（核心风险控制）

#### 5.4.1 双写机制设计

1. **双写触发**：所有写操作（新增/修改/删除）通过接口层路由同时触发v1、v2写操作；
2. **一致性校验**：
   - 实时校验：双写后立即对比v1/v2数据结果，差异率>0.001%时触发告警；
   - 批量校验：每日全量对比核心表数据，输出《双写一致性报告》；
3. **异常处理**：双写失败时，自动重试3次，重试失败则暂停v2流量，触发人工介入。

#### 5.4.2 一键回滚设计

1. **回滚触发条件**：核心业务故障、双写差异率超标、性能不达标等P0/P1级问题；
2. **回滚流程**：
   - 步骤1：网关层立即将100%流量切回v1；
   - 步骤2：停止v2写操作，锁定v2数据；
   - 步骤3：通过备份工具将v1镜像数据同步至v2（如需）；
   - 步骤4：验证v1系统状态，确认回滚完成；
3. **回滚工具**：开发自动化回滚脚本，包含流量切换、数据锁定、数据恢复等功能，保证30分钟内完成全流程。

### 5.5 多人实时协作模块（Phase 2核心）

#### 5.5.1 设计目标

支持10人同时编辑同一模型，无数据冲突/丢失，同步延迟<100ms。

#### 5.5.2 实现方案

1. **基于Yjs的协作核心**：集成Yjs实现前端实时数据同步，保证操作一致性；
2. **冲突解决**：基于v1业务规则制定冲突优先级（如"最后编辑者生效"+关键字段锁定）；
3. **数据同步**：通过Supabase实时数据库实现前端-后端数据同步，减少延迟；
4. **性能优化**：分片同步大表格数据，仅同步变更部分，降低传输开销。

### 5.6 数据迁移模块（Phase 0.2核心）

#### 5.6.1 迁移范围

v1所有核心业务表、配置表、历史数据，覆盖100%v1业务数据。

#### 5.6.2 迁移方案

1. **全量迁移**：Phase 0.2完成v1生产环境数据镜像全量迁移至v2，输出《数据迁移报告》；
2. **增量同步**：全量迁移后，通过binlog同步v1增量数据至v2，保证数据实时一致；
3. **一致性验证**：迁移后对比v1/v2数据条数、字段值、计算结果，通过率100%方可进入Phase 1；
4. **回滚预案**：迁移失败时，立即恢复v1数据镜像，终止v2迁移流程，重新制定方案。

## 六、T4架构设计与PRD/资产复用的协同规则

### 6.1 三者协同关系

| 工作内容 | 核心输出 | 互相验证点 |
|------------------|-----------------------------------|----------------------------------------------------------------------------|
| 架构设计 | 技术方案、风险控制方案 | 验证PRD是否可技术实现，验证资产复用的技术可行性 |
| PRD精细化 | 固化v1 Spec、一致性验收标准 | 为架构设计提供需求边界，验证架构方案是否满足业务兼容性 |
| 资产复用分析 | 复用/重构清单、技术依赖 | 为架构设计提供输入，验证PRD中复用部分的完整性 |

### 6.2 协同机制

1. **每日同步会**：Phase 0.2期间，架构师、产品经理、核心开发每日同步进度，解决协同中的冲突；
2. **交叉评审**：架构师评审PRD中技术可行性，产品经理评审架构方案是否满足业务兼容，资产分析结果同步至双方；
3. **版本同步**：PRD/架构/资产分析文档使用同一版本号，修改后互相通知，保证信息一致。

## 七、T4架构设计的阶段化落地规则

### 7.1 Phase 1：核心功能落地

1. 仅落地公式引擎、基础编辑、Excel导入导出等核心功能的架构方案；
2. 双写机制仅部署至测试环境，验证计算一致性；
3. 灰度流量仅开放1%-5%，聚焦核心功能验证。

### 7.2 Phase 2：协作与后端落地

1. 部署Yjs协作模块、Supabase后端架构；
2. 双写机制扩展至预生产环境，全量验证数据一致性；
3. 灰度流量逐步提升至100%，验证协作场景稳定性。

### 7.3 Phase 3：AI助手落地（可选）

1. 集成RAG向量知识库架构，不侵入核心计算流程；
2. 独立部署AI模块，与核心系统解耦，故障不影响主流程。

## 八、T4架构设计变更规则

1. **变更触发条件**：仅允许因立项约束调整、v1资产复用分析重大变更、核心风险点新增触发架构变更；
2. **变更审批流程**：
   - 提交《架构变更申请》，说明变更原因、影响范围、风险；
   - 经技术负责人+业务负责人+测试负责人审批；
   - 重大变更需更新立项文档，并重新走L4审查；
3. **变更落地**：变更后需重新验证相关方案（如回滚演练、数据一致性校验），输出变更验证报告。

## 九、T4架构设计验收标准（Phase 0 L4审查）

### 9.1 量化验收指标

| 指标 | 要求值 | 验证方法 |
|----------------------|---------------------------------|-----------------------------------|
| 资产复用率 | ≥90% | 核对《资产复用分析报告》|
| 回滚流程耗时 | ≤30分钟 | 回滚演练计时 |
| 双写差异率 | ≤0.001% | 自动化校验工具批量对比 |
| 公式计算误差 | <0.0001% | 1000+测试用例全量验证 |
| 架构方案覆盖v1功能 | 100% | 对照v1 Spec逐条核对 |

### 9.2 非量化验收标准

1. 所有架构决策对齐立项约束，无偏离；
2. 核心风险方案（双写/回滚/迁移）经过演练验证；
3. 架构文档与PRD/资产分析文档信息一致，无冲突；
4. 所有审查参与方（技术/业务/测试/运维）达成共识。

## 十、风险与应对措施

| 风险点 | 触发条件 | 应对措施 |
|------------------------|------------------------------|--------------------------------------------------------------------------|
| 公式计算结果不一致 | 双写对比差异率>0.001% | 暂停流量切换，定位函数映射/计算逻辑问题，重新执行全量校验 |
| 数据迁移失败 | 数据丢失/损坏/不一致 | 立即回滚至v1镜像，修复迁移脚本后重新迁移，全量验证通过后方可继续 |
| 协作场景数据冲突 | 多人编辑同一字段 | 触发冲突解决规则，锁定关键字段，记录操作日志，支持冲突回滚 |
| 系统性能不达标 | 页面加载>3s/计算>100ms | 暂停新功能开发，优化缓存策略、数据分片、代码逻辑，重新压测 |
| 回滚流程超时 | 回滚操作>30分钟 | 启用应急回滚脚本，优先切换流量至v1，后续再处理v2数据恢复 |

## 附录：T4架构设计核心原则速查

### A.1 约束性原则（优先级最高）

1. **100%兼容性原则**：
   - 公式计算结果与v1误差<0.0001%，所有v1的Excel模板、导出文件、数据库结构在v2中完全可用；
   - 业务逻辑、用户操作习惯、界面布局、快捷键与v1零差异，无UI改版。
2. **风险可控原则**：
   - 强制双写机制：v2上线初期与v1并行运行，双写周期≥3个月；
   - 一键回滚保证：30分钟内可完整回滚至v1，回滚后数据零丢失；
   - 灰度发布强制：流量切换按1%→5%→20%→50%→100%分阶段执行，每个阶段观察≥7天。
3. **技术栈约束原则**：
   - 仅引入HyperFormula（公式引擎）、Yjs（多人协作）、Supabase（后端）三类新技术，无其他未经验证的技术引入。
4. **开发模式原则**：
   - 业务层100% Spec Coding，先写Spec再生成代码；
   - 架构设计与PRD精细化、资产复用分析并行，所有决策基于v1资产复用分析结果。

### A.2 非约束性原则

1. **复用优先**：最大化复用v1可复用资产（如核心业务逻辑Spec、数据库表结构、通用工具类），减少重复开发；
2. **可扩展性**：在兼容v1的基础上，为Phase 2多人协作、Phase 3 AI助手预留扩展接口；
3. **可观测性**：全链路监控覆盖核心流程，支持性能、错误、数据一致性的实时监控与告警；
4. **可测试性**：架构设计需适配自动化测试、双写对比测试、灰度流量验证等测试场景。
