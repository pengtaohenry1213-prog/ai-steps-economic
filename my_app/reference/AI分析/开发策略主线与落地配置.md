# 项目主线与落地配置

## 2.1 项目主线

**定位/作用**：项目的核心行动纲领，是贯穿全流程的核心方向

> 在 100% 兼容 v1 业务逻辑和数据的前提下，分阶段完成核心技术栈换代，逐步引入多人协作和 AI 智能能力，最终实现系统性能、可靠性和协作效率的全面提升。

---

## 2.2 核心配置要点

**定位/作用**：围绕项目主线落地的具体规则（开发模式、Human Gate 等级、关键模块配置、风险控制等），是主线落地的保障

### 2.2.1 开发模式总原则

- **业务层：100% Spec Coding**：所有业务逻辑必须与v1完全一致，不允许任何"优化"或"改进"
- **技术层：分阶段混合模式**：
  - Phase 1（核心功能）：90% Spec + 10% Vibe
  - Phase 2（协作+后端）：80% Spec + 20% Vibe
  - Phase 3（AI助手）：70% Spec + 30% Vibe

### 2.2.2 分阶段Human Gate等级

| 阶段 | 核心任务 | Human Gate等级 | 审查重点 |
|------|----------|----------------|----------|
| Phase 0 | 资产复用分析与方案设计 | L4（极其严格） | 兼容性方案、数据迁移方案、回滚预案 |
| Phase 1 | 表格+公式引擎+版本管理 | L3（严格） | 公式计算一致性、数据格式兼容性 |
| Phase 2 | Yjs协作+Supabase后端 | L3→L4 | 数据一致性、并发冲突处理 |
| Phase 3 | RAG智能助手 | L2（标准） | 功能正确性、安全性 |

### 2.2.3 关键模块配置

| 模块 | 开发模式 | Human Gate等级 | 说明 |
|------|----------|----------------|------|
| 公式引擎迁移 | 100% Spec | L4 | 必须与v1计算结果完全一致，逐函数验证 |
| 数据迁移与兼容层 | 100% Spec | L4 | 数据零丢失，格式100%兼容 |
| 版本状态机 | 100% Spec | L3 | 完全复用v1权限控制矩阵 |
| Yjs协作层 | 90% Spec + 10% Vibe | L3 | 重点验证冲突解决和数据一致性 |
| RAG智能助手 | 70% Spec + 30% Vibe | L2 | 独立于核心计算流程，不影响业务逻辑 |

### 2.2.4 核心风险控制

- **双写机制**：上线初期同时运行v1和v2系统，对比计算结果
- **灰度发布**：按用户、按模型逐步切换流量，每个阶段至少观察1周
- **一键回滚**：任何时候都能在30分钟内回滚到v1系统
- **全量回归测试**：所有v1功能必须在v2上通过完整回归测试

## 2.3 AI 角色与阶段/模块映射

**定位/作用**：为项目主线落地匹配对应的 AI 角色体系，明确不同阶段/模块的 AI 分工，是主线落地的资源配置支撑

### 2.3.1 整合思路

基于 `.cursor/settings.json` 中定义的 AI 角色体系，将**角色分类+具体角色** 映射到「阶段」「模块」维度，同时关联对应的规则文件，确保配置与角色体系一致。

### 2.3.2 阶段维度映射

| 阶段 | 关联AI角色 | 角色规则文件 | 说明 |
|------|-----------|-------------|------|
| 需求规划 | Planner Agent、PM Agent、PMO Agent | .cursor/rules/planner.mdc、PM.mdc、PMO.mdc | 需求拆解、计划制定 |
| 开发实现 | Frontend Agent、Backend Agent、各技术栈角色 | react.mdc、fastapi-python.mdc、vuejs-typescript-best-practices.mdc 等 | 前端/后端/专项开发 |
| 测试验证 | Test Agent、Test Human Gate Agent | .cursor/rules/TEST.mdc | 用例设计、测试执行 |
| 代码评审 | Reviewer Agent、Reviewer Human Gate Agent | .cursor/rules/reviewer.mdc | 代码质量、规范检查 |
| 部署发布 | Deploy Agent、Security Agent | .cursor/rules/deploy-rules.mdc | 环境部署、安全校验 |
| 问题排查 | Troubleshooting Agent、DBA Agent | .cursor/rules/troubleshoot-issues.mdc | 故障定位、数据库排查 |
| 人机审核 | 各Human Gate角色（PM/PMO/技术负责人等） | .cursor/prompts/*-human-gate.md | 关键节点人工审批 |

### 2.3.3 模块维度映射

| 模块 | 关联AI角色 | 角色规则文件 | 说明 |
|------|-----------|-------------|------|
| 产品设计 | PM Agent、UI Agent、UX Agent | .cursor/rules/PM.mdc | 产品需求、交互/视觉设计 |
| 前端开发 | Frontend Agent、React/Vue3/Next.js Agent | frontend.mdc、vuejs-typescript-best-practices.mdc 等 | 多框架前端开发 |
| 后端开发 | Backend Agent、FastAPI/Go/Java/PHP Agent | fastapi-python.mdc、go.mdc 等 | 多语言后端开发 |
| 全栈开发 | Fullstack Agent | .cursor/rules/react+supabase.mdc | 前后端一体化开发 |
| 测试模块 | Test Agent、Test Human Gate Agent | .cursor/rules/TEST.mdc | 自动化/手动测试 |
| 安全模块 | Security Agent、Security Human Gate Agent | .cursor/rules/security-rules.md | 漏洞扫描、权限管控 |
| 数据库模块 | DBA Agent | .cursor/rules/database.mdc | 建表、优化、备份 |
| 专项开发 | Chrome Extension/Android Agent | chrome-extension.mdc、android.mdc | 浏览器插件/安卓开发 |
| 流程管控 | Tech Lead Agent、PMO Agent | .cursor/rules/tech-lead.mdc | 技术方案、项目进度管控 |

### 2.3.4 补充说明

1. **角色关联逻辑**：
   - 「阶段」维度按项目生命周期映射角色，覆盖从规划到上线的全流程；
   - 「模块」维度按功能域映射角色，聚焦具体业务模块的职责分工；
   - 所有角色均严格对应 `settings.json` 中 `cursorrules.roles` 下的定义，规则文件路径与配置中 `rules` 字段完全一致。

2. **扩展建议**：
   - 若需细化「技能维度」，可补充 `settings.json` 中 `cursorrules.skills` 下的技能项（如 agent-development、frontend-design 等），作为「模块/阶段」的子属性；
   - 执行流程类技能（run-all/run-step/execute-plan）可关联到「阶段」的"流程管控"子项，用于定义 AI 角色的执行规则。

3. **格式适配**：
   - 若《项目类型判定与核心配置结论》为表格/文档形式，可直接复用上述表格结构；
   - 若为配置文件形式，可参考 `settings.json` 的层级结构，将「阶段/模块」作为一级节点，嵌套对应AI角色及规则路径。
