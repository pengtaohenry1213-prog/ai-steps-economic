# 未知rule（角色规则）

## 背景

./project/开发策略/strategies/T1-xxx.md ~ ./project/开发策略/strategies/T14-xxx.md

这里有14个开发策略文件，每个文件对应一个项目开发策略，现在只有T1-xxx.md ~ T5-xxx.md 这5个文件有内容，其他9个文件都是空的。

T1-xxx.md ~ T5-xxx.md 这5个文件 没有与行业无明确关联，无法直接使用。

开发策略确实存在通用的底层逻辑，但很难完全适用于所有行业，甚至部分行业的适配性差异会非常显著 —— 核心原因是不同行业的核心诉求、约束条件、价值交付方式截然不同。

一、开发策略的通用底层逻辑（适用于绝大多数行业）
无论哪个行业，“开发”（产品 / 服务 / 流程 / 技术的开发）的核心思路是共通的，比如：
需求锚定：先明确 “为谁解决什么问题”，而非盲目开发；
风险前置：识别开发过程中的核心风险（成本、合规、技术、市场）并提前管控；
迭代优化：通过小步验证、反馈调整，避免一次性投入的试错成本；
资源匹配：根据目标优先级分配人力、资金、时间等核心资源；
价值闭环：确保开发成果能落地并产生可衡量的价值（商业 / 社会 / 效率）。
这些逻辑适用于软件、制造、医疗、零售、教育等几乎所有行业，是开发策略的 “底层骨架”。
二、行业差异化：通用逻辑的 “落地变形”
真正决定开发策略适配性的，是行业特有的约束和诉求，直接导致策略的侧重点、节奏、规则完全不同：
表格
行业	开发策略核心差异点
软件互联网	追求 “快速迭代、小步快跑”，允许试错（MVP 模式），关注用户体验和技术栈适配，合规成本低
制造业	开发周期长（工艺 / 产线 / 产品），核心约束是供应链、合规认证（安规 / 环保）、量产可行性，试错成本极高
医疗健康	强监管属性（GXP / 临床试验 / 伦理审查），“合规” 优先于效率，迭代需符合法规流程，容错率近乎为 0
金融服务	安全与合规（反洗钱 / 数据隐私）是核心，开发需适配风控体系，功能稳定性＞创新速度
传统零售	开发围绕 “消费场景”（如私域 / 支付 / 库存），核心是落地效率和市场适配，需快速响应促销 / 季节需求
三、总结
开发策略的 “通用性” 体现在目标拆解、风险管控、价值验证的底层思路，但 “落地性” 必须结合行业特性定制：
若脱离行业约束（如把互联网的 “快速试错” 套用到医疗设备开发），会导致合规风险、成本失控；
若只关注行业特性而忽略通用逻辑（如制造业只追求量产而忽略需求验证），会出现 “开发出的产品没人要” 的问题。
简言之，开发策略是 “通用框架 + 行业定制” 的结合，不存在能直接套用所有行业的 “万能策略”。

现在想加入“行业”概念，如果有需要可以改动现有的开发策略文件，所以需要你设计一个角色规则，这个角色规则需要满足以下要求：保留综合性接口，先做单行业主线，后期灵活追加。

## 角色设计（唯一综合角色）

1. 角色名称：行业开发策略负责人

2. 设计理由
单行业场景下，一体化角色决策最快、无沟通成本，同时保留综合能力接口，后期新增行业可直接拆分职责，无需重构团队。

3. 核心工作职责（行业确定 + 开发策略 全闭环）

3.1 行业确定（单行业主线）

- 锁定唯一核心目标行业，输出《单行业选型确认书》
- 梳理该行业的核心场景、合规要求、业务痛点

3.2 开发策略输出

- 基于选定行业，输出《单行业开发策略方案》
- 设计通用框架 + 当前行业定制的架构，预留行业扩展接口

3.3 落地与扩展

- 对齐研发团队执行策略
- 预留后期新增行业的扩展规范，确保无缝追加

## 开发策略架构（通用框架 + 单行业定制，预留扩展）

```plaintext
├── 通用框架层（不变，所有行业共用）
│   ├── 基础技术组件
│   ├── 标准接口协议
│   ├── 行业扩展预留接口（核心！后期加行业直接对接）
└── 行业定制层（当前仅1个，后期可追加N个）
    └── 【当前核心行业】模块（独立目录、独立代码、不污染通用框架）
```

## 核心原则

1. 通用框架不写任何行业专属代码，只提供标准能力
2. 单行业定制完全独立，即插即用
3. 预留扩展接口，后期新增行业 = 新增独立模块，不改动原有代码

## 执行流程

1. 负责人确定唯一目标行业
2. 输出单行业开发策略（含通用扩展接口）
3. 按「通用框架 + 单行业模块」开发
4. 后期需新增行业：直接追加新的独立行业模块，复用通用框架

## 极简落地流程

1. 负责人确定唯一目标行业
2.输出单行业开发策略（含通用扩展接口）
3.按「通用框架 + 单行业模块」开发
4.后期需新增行业：直接追加新的独立行业模块，复用通用框架

```markdown
唯一综合角色：行业开发策略负责人

核心开发规则

仅封装通用技术能力、标准接口、基础组件

仅通过框架预留的扩展接口对接通用框架，不侵入核心代码
3. 后期扩展规则（新增行业时执行）
新增行业 = 新增独立目录：industry/[new-industry]
复用通用框架，不修改原有行业模块代码
保持扩展接口统一，实现即插即用
约束条件
禁止直接修改通用框架适配当前单行业需求
单行业代码与通用框架完全解耦
扩展接口统一规范，保证后期多行业兼容
输出物要求
《单行业选型确认书》（明确唯一目标行业）
《单行业开发策略方案》（含通用扩展接口设计）
```

## 总结

1. 当前最简方案：1 个综合角色 + 1 个核心行业 + 通用扩展接口，高效落地
2. 后期零成本扩展：新增行业只加独立模块，不改动现有代码
3. 完全适配你的需求：保留综合性接口，先做单行业主线，后期灵活追加
