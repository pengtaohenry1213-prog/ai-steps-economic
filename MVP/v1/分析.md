# v1 升级到 v2 前是否需要 MVP/MVT 分析

## Context

当前项目处于 v1 向 v2 迁移的关键节点。v1 已完整实现：vxe-table 表格、公式计算引擎（自研）、Mock 数据、Excel 导入导出。v2 的目标架构（vxe-table + HyperFormula + Yjs CRDT 协作）只有设计文档，**核心功能代码尚未实现**。

核心问题是：在投入大量时间构建 v2 MVP 之前，是否需要先做技术验证？

## 结论：**✅ 已确认：先做 MVT（最小可行技术验证）**

用户已确认采用 MVT 优先策略，先验证核心技术可行性（2-3 周），通过后再投入 MVP 开发（4-6 周）。

### 理由

1. **核心技术风险高**：HyperFormula 与 v1 公式语法不兼容（v1 用 `${metricCode-year}`，HF 用 `A1` 语法）
2. **绑定复杂度高**：vxe-table + HyperFormula + Yjs 三者集成没有先例验证
3. **避免后期返工**：MVT 验证失败可及时调整方案

## MVT 验证范围（2-3 周）

| 验证点 | 方法 | 成功标准 |
|--------|------|----------|
| **vxe-table + HyperFormula 绑定** | 创建基础集成 demo，双向同步编辑-计算-显示 | 编辑单元格 → 公式重算 → 显示结果，延迟 < 100ms |
| **v1 公式语法转换** | 选取 10 个 v1 典型公式，手动转换为 HF 语法并对比结果 | 转换后计算结果 100% 一致 |
| **财务函数兼容性** | 对比 v1 XIRR/NPV/IRR 与 HyperFormula 结果差异 | XIRR 一致；NPV/IRR 如有差异需使用 v1 实现 |
| **Yjs 状态同步**（可选） | 验证 Y.Doc 与 vxe-table 数据模型映射 | 多用户同步延迟 < 100ms |

### MVT 里程碑

```
Week 1: vxe-table + HyperFormula 基础绑定
Week 2: v1 公式样本转换验证（10 个样本）
Week 3: 财务函数兼容性验证 + Yjs（可选）
```

## 如果 MVT 通过，MVP 范围建议（4-6 周）

### Phase 1: 核心功能

| 周次 | 任务 |
|------|------|
| Week 1 | VxeTableWrapper 封装 + Mock Service + 模型/版本列表页 |
| Week 2 | HyperFormula 集成 + v1 财务函数补充 + 单元格编辑 |
| Week 3 | 版本状态机 + 保存/加载 + 权限控制 |
| Week 4 | Excel 导入导出 + 数据格式化 + 单元测试 |

### Phase 2: 协作功能（可选，2 周）

- Yjs 实时同步
- 光标同步
- 冲突解决

## 风险缓解策略

1. **混合公式引擎**：HyperFormula 作为核心，v1 XIRR/NPV/IRR 作为补充（HF缺少 XNPV，NPV/IRR 算法与 v1 不同）
2. **公式转换层**：渐进式迁移，不用一次性解决所有兼容性问题
3. **MVT 优先**：先验证技术可行性，再投入 MVP 开发

## 验证方法

MVT 完成后，通过以下步骤验证：
1. 加载 v1 Mock 数据（3 模型 + 3 版本）
2. 在 v2表格中渲染相同数据
3. 对比 v1 和 v2 的公式计算结果
4. 验证 Excel 导入导出结果一致性
