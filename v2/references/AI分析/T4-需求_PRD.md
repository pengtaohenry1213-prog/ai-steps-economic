## B. v1资产全量盘点与基线建立（2天）

**目标**：建立v1的"黄金基线"，作为所有PRD需求的唯一参考标准

### B.1 v1资产清单梳理

- **代码资产**：前端所有组件、后端所有接口、公式引擎核心代码、Excel导入导出代码
- **数据资产**：数据库表结构、生产环境脱敏数据、所有Excel模板文件
- **文档资产**：v1需求文档、设计文档、测试用例、用户手册
- **行为资产**：录制v1所有核心操作流程的视频（包括异常场景）

**AI辅助**：让Planner Agent扫描v1代码库，自动生成资产清单和模块依赖关系图

### B.2 v1核心功能点枚举

按照业务模块枚举v1所有功能点，形成《v1功能点全量表》：

| 模块 | 功能点 | 优先级 | 是否核心功能 | 备注 |
|------|--------|--------|--------------|------|
| 模型管理 | 创建模型 | P0 | 是 | |
| 模型管理 | 删除模型 | P1 | 否 | |
| 版本管理 | 创建版本 | P0 | 是 | |

| 公式计算 | SUM函数 | P0 | 是 | |
| 公式计算 | XIRR函数 | P0 | 是 | 特殊算法 |

**要求**：功能点粒度要细到"每个按钮、每个输入框、每个公式"，确保没有遗漏

### B.3 v1行为基线确认

- 对每个核心功能点，记录v1的**精确行为**，包括正常流程和异常流程
- 对每个公式，记录v1的计算结果（使用固定测试数据）

**关键要求**：**"所见即所得"**，v1怎么做，v2就必须怎么做。哪怕v1有bug，只要不是致命bug，v2也必须原样复现。

## C. 分模块Spec固化（5天）

**目标**：将v1的隐式业务逻辑转化为显式的、可执行的Spec文档

### C.1 公式引擎模块Spec（最核心，优先级最高）

这是整个PRD中最重要的部分，直接决定升级的成败

1. **公式语法Spec**
   - 完整定义v1支持的所有公式语法，包括变量格式（`${metricCode-year}`）、运算符、函数参数
   - 列出所有v1支持的函数，包括每个函数的参数个数、参数类型、返回值类型
   - 明确公式的解析顺序、优先级、结合性

2. **函数行为Spec**
   - 对每个函数，详细描述其计算逻辑
   - 提供每个函数的**测试用例集**，包括正常输入、边界输入、异常输入
   - 明确每个函数的精度要求（误差<0.0001%）

3. **计算流程Spec**
   - 定义v1的完整计算流程：数据加载->依赖分析->拓扑排序->公式计算->结果展示
   - 明确循环依赖的处理方式、错误提示方式
   - 定义计算缓存机制、增量计算规则

**AI辅助**：让Test Agent读取v1公式引擎代码，自动生成每个函数的测试用例集

### C.2 数据模型Spec

1. **数据库表结构Spec**
   - 完整复制v1的所有表结构，包括字段名、字段类型、长度、约束、索引
   - 明确每个字段的业务含义、取值范围、默认值
   - 定义表之间的关联关系、级联规则

2. **内存数据模型Spec**
   - 定义v1前端使用的所有数据结构
   - 明确数据的转换规则（数据库->内存->UI）

3. **Excel格式Spec**
   - 定义v1导入导出的Excel模板格式
   - 明确导入时的数据校验规则、错误处理方式
   - 定义导出时的样式规则、公式保留规则

### C.3 版本状态机与权限控制Spec

1. **版本状态机Spec**
   - 完整定义v1的版本状态流转图：草稿->已提交->已锁定
   - 明确每个状态的允许操作、状态转换条件
   - 定义版本锁定/解锁的规则、权限

2. **权限控制Spec**
   - 完整复制v1的权限控制矩阵
   - 明确每个角色在每个版本状态下的操作权限
   - 定义数据访问权限、功能操作权限

### C.4 UI交互与用户体验Spec

1. **界面布局Spec**
   - 定义v1所有页面的布局结构、组件位置、尺寸
   - 明确表格的列顺序、列宽、排序规则、筛选规则
   - 定义单元格的样式规则（加粗、斜体、红色、背景色）

2. **交互行为Spec**
   - 定义所有用户操作的交互流程，包括点击、双击、右键、快捷键
   - 明确错误提示的内容、位置、样式
   - 定义加载状态、空状态的展示方式

**关键要求**：**像素级还原**。v2的界面和交互必须与v1完全一致，用户不需要任何学习成本就能使用。

## D. 分阶段需求拆解（3天）

**目标**：将固化的Spec按照项目里程碑拆分为可执行的开发任务

### D.1 按阶段划分需求优先级

根据Phase 0-3的里程碑，将所有功能点分配到对应的阶段：

| 阶段 | 包含模块 | 核心需求 |
|------|----------|----------|
| **Phase 1** | 表格编辑、公式引擎、版本管理、Excel导入导出 | 所有P0核心功能 |
| **Phase 2** | Yjs多人协作、Supabase后端、监控告警 | 协作能力、后端升级 |
| **Phase 3** | RAG智能助手 | 新增功能 |

**原则**：
- 所有P0核心功能必须在Phase 1完成
- 非核心功能可以放到Phase 2或Phase 3
- 新增功能绝对不能影响核心功能的迁移

### D.2 每个需求点的精细化拆解

对每个需求点，按照以下格式进行拆解：

```markdown
### 需求ID：REQ-001
### 需求名称：[名称]

### 需求描述：[描述]
### 输入输出：
- 输入：[输入描述]
- 输出：[输出描述]
### 业务规则：
1. [规则1]
2. [规则2]
### 一致性验收标准：
1. [标准1]
2. [标准2]
### 依赖关系：[依赖]
### 估算工作量：[X人天]
### 负责人：[负责人]
```

**关键要求**：
- 每个需求点的工作量不超过2人天
- 每个需求点必须有明确的**一致性验收标准**
- 明确每个需求点的依赖关系

### D.3 生成任务WBS

将拆解后的需求点转化为项目任务WBS，导入到项目管理工具（Jira/Trello）中，明确每个任务的负责人、起止时间、依赖关系。

## E. 兼容性与风险识别（2天）

**目标**：在PRD中明确所有可能的兼容性问题和风险，并制定应对措施

### E.1 技术兼容性风险识别

- 公式语法差异：HyperFormula与v1自研引擎的语法差异
- 数据类型差异：JavaScript与PostgreSQL的数据类型转换问题
- 第三方库差异：exceljs新版本与v1使用版本的差异
- 浏览器兼容性：新代码在不同浏览器下的行为差异

### E.2 业务兼容性风险识别

- 历史数据迁移：v1历史数据导入v2后的一致性问题
- Excel模板兼容性：v1的旧模板在v2中无法正常使用
- 用户习惯变化：哪怕微小的交互变化都可能导致用户投诉
- 第三方系统集成：与其他系统的接口兼容性问题

### E.3 风险应对措施

对每个识别出的风险，制定对应的应对措施：

| 风险ID | 风险描述 | 影响等级 | 应对措施 | 负责人 |

| RISK-001 | [风险描述] | 高 | [应对措施] | [负责人] |
| RISK-002 | [风险描述] | 高 | [应对措施] | [负责人] |

## G. PRD评审与确认（1天）

### G.1 内部评审

组织项目核心成员（技术负责人、测试负责人、v1原开发人员）进行内部评审，重点审查：

- PRD是否100%覆盖了v1的所有核心功能
- 所有需求点的验收标准是否明确、可执行
- 所有识别出的风险是否都有应对措施
- 分阶段需求划分是否合理

### G.2 业务方评审

邀请业务方代表和最终用户进行评审，重点确认：

- PRD描述的业务逻辑与v1的实际行为是否一致
- 所有用户关心的功能点都已包含
- 升级后的用户体验是否符合预期

### G.3 签字确认

所有评审人员在PRD上签字确认，PRD正式生效。生效后的PRD是后续开发、测试、验收的唯一依据。任何变更必须经过正式的变更流程。

## 关键注意事项

1. **绝对不允许修改v1的业务逻辑**：哪怕v1的逻辑看起来不合理，只要不是致命bug，v2也必须原样复现。所有业务逻辑的修改必须在升级完成后单独进行。
2. **所有需求必须可验证**：每个需求点都必须有明确的、可量化的验收标准，不能有"尽量"、"大概"这样的模糊描述。
3. **PRD是活文档**：在项目过程中，如果发现v1有未覆盖的行为或新的风险，必须及时更新PRD，并通知所有相关人员。
4. **AI是辅助工具**：AI可以提高效率，但最终的需求确认和责任必须由人类承担。所有AI生成的内容都必须经过人工仔细审查。
