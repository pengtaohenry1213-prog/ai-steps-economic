# T3 - 成熟型新项目开发策略（软件互联网行业）

## 基本信息
- **策略**: T3 - 成熟型新项目
- **行业**: software - 软件互联网
- **置信度**: 85%

## 匹配推理
- **推理**: 项目是基于新技术栈（Vue 3 + TypeScript + Vite）构建新版本平台（v2），业务需求明确（经济模型协作平台），技术栈成熟，目标是高效标准化交付并复用部分数据库设计。
- **判断依据**: 选择T3而非T4：项目不是在现有核心生产系统上进行零中断架构重构，而是基于新架构构建新一代平台，属于新项目交付范畴；选择T3而非T2：技术栈明确且成熟，迁移路径清晰，不存在高度不确定性；选择T3而非T5：这是全新系统构建，而非在成熟系统上的功能迭代。

## 策略定义
针对业务需求明确、技术栈成熟、经济模型在线协作平台（v2升级版）的高效标准化交付策略。核心目标是充分利用v1既有资产，在成熟技术栈基础上实现快速迭代交付。

## 适用场景
1. 业务需求明确，有详细的产品规格说明（Spec 01-07完整）
2. 技术栈成熟稳定（Vue3 + TypeScript + Vite生态）
3. 有明确的上线时间和交付里程碑
4. 存在可复用的历史资产（v1数据库设计、组件库）
5. 团队具备丰富的前后端分离开发经验

## 不适用场景
1. 业务需求模糊或频繁变更（建议使用T1/T2）
2. 需要大规模技术架构重构（建议使用T4）
3. 首次探索性技术选型阶段
4. 团队技术积累不足的新兴领域

## 核心特点
1. 业务需求：明确且详细（7个Spec文档支撑）
2. 技术风险：低（成熟技术栈 + 可复用资产）
3. 交付压力：效率优先（标准化流程 + 资产复用）
4. 团队特征：经验丰富（Turborepo Monorepo组织）

## 核心矛盾
在保证交付效率的同时，确保v1到v2的平滑迁移和资产最大化复用，同时维持代码质量和可维护性。

## 分阶段开发
### 阶段一：基础设施与资产复用
- 目标: 完成项目脚手架搭建、团队开发环境统一、v1数据库资产审计与复用方案制定
- 开发模式: 框架搭建 + 代码生成
- Human Gate: L2 - 架构评审通过
- 核心交付物: Monorepo项目结构、数据库Schema（基于v1优化）、开发规范文档、CI/CD流水线
- 成功标准: 团队全员开发环境5分钟内完成初始化、数据库DDL审查通过率100%

### 阶段二：核心模块迭代开发
- 目标: 基于Spec完成核心业务模块开发（数据模型、公式引擎、页面配置），持续集成与质量保障
- 开发模式: 迭代开发 + 持续交付
- Human Gate: L3 - PR审查 + 自动化测试覆盖
- 核心交付物: 数据模型管理模块、HyperFormula公式引擎集成、页面配置系统、单元测试（覆盖率>80%）
- 成功标准: 核心模块E2E测试通过率100%、性能基准达标（P95 < 200ms）

### 阶段三至四：简略描述
- 目标: 集成测试、系统联调、上线部署与运维监控
- 开发模式: 标准化交付
- Human Gate: L4 - 生产环境发布审批
- 核心交付物: 完整系统集成报告、监控告警配置、运维文档、用户手册
- 成功标准: 生产环境零P0故障、SLO达标率99.9%


## 关键注意事项
1. v1数据库资产（sql/01_tables.sql）是核心复用基础，开发前必须完成Schema审计和兼容性评估
2. Turborepo Monorepo架构下，共享依赖（HyperFormula、Tailwind配置）需统一管理，避免版本碎片
3. vxe-table作为核心UI组件，需封装业务组件层（而非直接使用），便于后续维护和扩展
4. 公式引擎是项目核心竞争力，v1财务函数迁移需要逐个验证，建议建立回归测试用例库
5. Mock Service设计需与最终后端API保持接口一致性，避免联调时大规模改动

## 推荐工具链
- **阶段一**: Vite + Turborepo + ESLint + Prettier + Husky - 项目初始化、代码规范、Git Hooks自动化
- **阶段二**: Vitest + Playwright + Vue Test Utils + Storybook - 单元测试、E2E测试、组件文档化
- **阶段三+四**: GitHub Actions + Docker + Nginx + Grafana/Prometheus - CI/CD流水线、容器化部署、监控告警

## 典型风险
### 资产复用风险
- **具体风险**: v1数据库设计与v2业务需求存在Gap，导致Schema需要大幅调整
- **应对措施**: 阶段一即启动数据库评审会议，输出兼容性报告和Schema演进计划

### 公式引擎兼容性风险
- **具体风险**: HyperFormula与v1财务函数行为不一致，影响业务正确性
- **应对措施**: 建立公式测试用例库（至少200+用例），逐函数验证兼容性

### 前端性能风险
- **具体风险**: 大数据量场景下vxe-table渲染卡顿，影响用户体验
- **应对措施**: 引入虚拟滚动、优化缓存策略、设定性能基准测试门禁

### 团队协作风险
- **具体风险**: Monorepo多包并行开发导致依赖冲突或构建超时
- **应对措施**: Turborepo缓存策略优化、明确包依赖边界、CI阶段并行构建


## 成功指标
1. 交付效率：阶段二周期迭代速度达到2周/轮，代码质量门禁通过率100%
2. 技术质量：单元测试覆盖率≥80%，E2E测试覆盖率≥60%，无P0/P1级缺陷流出
3. 性能指标：首屏加载<2s，操作响应P95<200ms，支持1000+行数据编辑无卡顿
4. 业务准确性：公式计算结果与v1版本偏差率<0.01%，核心业务流程走通率100%
5. 运维指标：SLO达标率99.9%，MTTR<30min，自动化部署成功率>99%

## 行业适配
软件互联网行业特性要求：1）前后端分离架构下，Mock Service需与API设计同步进行；2）TypeScript强类型覆盖所有模块边界，防止运行时错误；3）Tailwind CSS需建立设计系统Token，保证UI一致性；4）数据模型平台的高并发写入场景需提前压测；5）合规要求：数据安全（脱敏）、权限控制（RBAC）需内置于架构设计。经济模型协作场景的核心差异在于公式引擎的复杂度和实时协作能力，这两点是技术方案的关键决策点。
