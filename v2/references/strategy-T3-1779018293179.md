# T3 - 成熟型新项目开发策略（软件互联网行业）

## 基本信息
- **策略**: T3 - 成熟型新项目
- **行业**: software - 软件互联网
- **置信度**: 85%

## 匹配推理
- **推理**: 项目需求明确，技术栈成熟（Vue 3 + TypeScript + Vite生态），有v1资产可复用，目标是基于新架构构建新一代平台，属于典型的业务需求明确、技术栈成熟的标准化交付场景。
- **判断依据**: 选择T3而非T4的原因：虽然描述中提到'升级目标'，但从'构建新一代'、明确的技术栈选型、可复用的v1资产等描述来看，这是一个在新架构上构建新版本平台的场景，而非对核心生产系统进行零中断架构重构的T4场景。T4典型场景是银行核心系统不停机升级，本项目更符合新版本平台构建的高效标准化交付特征。

## 策略定义
业务需求明确、技术栈成熟的新一代经济模型在线协作平台开发策略，核心目标是高效标准化交付，同时保证代码质量和可维护性。

## 适用场景
1. 业务需求已明确，有详细的产品规格说明（Spec）
2. 技术栈成熟稳定（Vue 3 + TypeScript + Vite）
3. 有明确的上线和迭代时间要求
4. 存在可复用的历史资产（v1数据库设计和业务逻辑）
5. 团队具备Vue3和TypeScript开发经验

## 不适用场景
1. 业务需求不明确或频繁变更（应使用T1/T2探索型策略）
2. 核心系统大规模升级重构（应使用T4稳定型策略）
3. 采用全新技术栈或未经验证的技术方案
4. 团队缺乏相关技术经验

## 核心特点
1. 业务需求：明确且详细，有v1版本参考
2. 技术风险：低，基于成熟技术栈
3. 交付压力：效率优先，需要快速迭代
4. 团队特征：经验丰富，职责清晰
5. 协作模式：标准化流程，强调复用

## 核心矛盾
在追求交付效率的同时，如何保证代码质量和可维护性，特别是涉及复杂财务公式计算（HyperFormula）和多模块协作（Monorepo架构）时的技术债务控制。

## 分阶段开发
### 阶段一：基础架构与核心模块（Week 1-6）
- 目标: 完成项目基础架构搭建和核心功能开发，包括Monorepo架构、Pinia状态管理、vxe-table集成、HyperFormula财务函数配置
- 开发模式: 团队协作模式 - 按模块分配责任人，daily standup同步进度
- Spec详细程度: 详细规格（Detailed Spec）- 包含UI设计稿、数据结构、API定义、测试用例
- Vibe比例: 3:7（30%探索创新，70%标准化实现）
- Human Gate: G2（核心模块由Tech Lead审查，常规模块自我审查）
- 核心交付物: Turborepo Monorepo 基础架构,TypeScript 类型定义完整覆盖,vxe-table 财务表格组件封装,HyperFormula 财务函数库集成,Pinia 状态管理方案设计,数据库表结构与v1复用策略文档,单元测试覆盖率达到70%以上
- 成功标准: 基础功能验收通过，表格渲染性能达标（1000行数据<100ms），公式计算准确性100%

### 阶段二：业务功能与集成（Week 7-12）
- 目标: 完成业务功能开发、数据模型管理、公式编辑、版本控制等核心功能，与Mock Service联调
- 开发模式: 功能模块制 - 按业务域划分（数据模型、公式引擎、页面配置、指标管理）
- Spec详细程度: 中等规格（Medium Spec）- 核心功能详细，边界功能简化
- Vibe比例: 2:8（20%体验优化，80%功能实现）
- Human Gate: G2（功能模块审查）+ G3（跨模块集成审查）
- 核心交付物: 数据模型CRUD与版本管理,公式编辑器和计算引擎,页面配置与视图切换,指标树形层级管理,Mock Service完整实现,E2E测试覆盖核心流程,Playwright 自动化测试套件
- 成功标准: 核心业务流程跑通，公式计算与Excel一致性>99%，无阻塞性bug


## 模块开发模式
- **基础架构层（packages/shared）**: 规范化开发模式 - 类型定义优先，统一工具函数，文档完善 (G3)
- **业务组件层（packages/ui）**: 组件库开发模式 - 原子化设计，Storybook文档，Props类型化 (G2)
- **状态管理层（packages/store）**: 领域驱动设计 - 按业务域划分store，清晰的actions命名 (G2)
- **公式引擎层（packages/engine）**: 核心算法开发模式 - TDD，边界测试全覆盖，文档详尽 (G3)
- **应用层（apps/web）**: 功能迭代模式 - 按页面/功能分配，PR驱动开发 (G2)

## 关键注意事项
1. Monorepo架构下需统一代码规范（ESLint + Prettier + Husky），避免仓库污染
2. v1数据库复用需仔细评估字段变更风险，建议新增字段而非修改现有字段
3. HyperFormula财务函数需与v1实现逐一对比验证，确保兼容性
4. vxe-table大规模数据渲染需优化虚拟滚动配置，建议测试10000行场景
5. Mock Service需支持localStorage持久化，便于开发调试

## 推荐工具链
- **阶段一**: Vite + Vue3 + TypeScript + Turborepo + Vitest + ESLint + Prettier + Husky + Storybook - 基础架构优先，测试驱动开发，组件先有文档再有实现
- **阶段二**: Playwright + Mock Service Worker + Pinia + localStorage + GitHub Actions - E2E测试覆盖核心路径，CI/CD自动化构建和测试

## 典型风险
### 技术风险
- **具体风险**: HyperFormula财务函数与v1实现不一致，导致计算结果偏差
- **应对措施**: 建立完整的财务函数测试用例库，与v1逐个函数对比验证，差异立即修复

### 进度风险
- **具体风险**: vxe-table封装复杂度过高，影响整体进度
- **应对措施**: 优先实现基础功能，复杂特性（合并单元格、公式单元格）预留buffer时间，必要时简化

### 协作风险
- **具体风险**: Monorepo多团队开发导致代码冲突和依赖混乱
- **应对措施**: 明确包依赖规则，shared包变更需通知相关团队，依赖版本锁定

### 质量风险
- **具体风险**: 快速迭代导致技术债务积累
- **应对措施**: 每个PR必须包含测试用例，定期技术债务回顾，阻塞性问题优先修复


## 成功指标
1. 所有核心业务功能可用，公式计算准确性达到100%
2. 单元测试覆盖率≥70%，E2E测试覆盖核心路径
3. 表格渲染性能：1000行数据<100ms，10000行数据<500ms
4. 与v1数据库兼容性验证通过，无数据迁移问题
5. CI/CD流水线稳定，构建时间<5分钟

## 行业适配
软件互联网行业强调快速迭代和用户体验，本策略特别关注：1）前端工程化（Turborepo Monorepo）提升团队协作效率；2）组件化开发（vxe-table封装）降低重复开发成本；3）测试覆盖（Vitest + Playwright）保障交付质量；4）性能优化（虚拟滚动、计算缓存）提升用户操作流畅度。同时，由于是经济模型平台，财务计算的准确性和稳定性是核心竞争力，必须作为最高优先级对待。
