## 背景

您好，项目A: v2/apps/web 生成流程：用户输入 -> 生成策略（策略匹配 -> 策略增强）-> 立项书 -> 需求 -> 架构 -> Steps 生成（包括拆分小step）-> 初始化；
项目B: v2/apps/workflow-dashboard 生成流程： 用户输入 -> 立项书 -> 需求 -> 架构 -> 初始化。

补充：两个项目的数据结构不同，属性字段名称也不同。

这两个项目，我计划合并成一个项目，这个合并项目工作的前期规划是由那个角色处理？

我先说说我的前期规划的理解。

项目 A 和项目 B 的数据格式是不一样的，从项目迁移的角度看：

如果把项目 A 迁移 到 项目 B， 要把项目A拆解，要大动数据结构 以适应 项目B， 我的项目A数据结构及测试已经是成熟的， 此次2个项目的合并的主要目的也是因为项目A成熟， 要应用项目A的成熟的AI的成果。我个人感觉 从 项目A 迁移到 项目B 风险大，数据逻辑层的工作量也大。

如果把项目 B 迁移 到 项目 A，项目 B 有优点有：UI界面层 操作流程细节已经完成 + 细化的流程。UI（应用层）可以直接迁移到项目A。项目A 要符合 项目B 的 生成流程，项目A 要细化成（分裂成）项目B 的流程（注：项目A列有的“策略匹配 -> 策略增强 是 项目B没有的，要与项目B 的生成流程 合并）。

你这个分析挺清晰的，A→B 风险大、B→A 收益更明显，我同意这个判断——B 那边的 UI 和流程细节是"皮"，A 的策略匹配/增强是"骨"，皮能包骨，骨不能削足适履。

我现在的角色：AI全栈开发工程师。

## 需要

我的实际建议：你不需要"按标准做"，你需要的是"参考绞杀者模式设计迁移路径 + 写几份 ADR 把决策固定下来 + 出一份数据映射表"。

### 三条最短学习路径

1. Strangler Fig Pattern（入门）

* Martin Fowler 原文：martinfowler.com/bliki/StranglerFigApplication.html（2004 首发，2014 重大更新，10 分钟读完）
* 关键点就是一句话：别想一次替换整个老系统，让新系统像藤蔓一样逐渐包裹它
* 然后看 1~2 个真实案例就懂了：
 	- Shopify 从 Rails monolith 拆分
 	- GitHub 从单体到模块化（GitHub 关于这个的工程博客）

2. ADR

* Michael Nygard 原文（也是 10 分钟读完）：cognitect.com/blog/2011/11/15/documenting-architecture-decisions
* 重点看 ADR 模板：标题、状态、上下文、决策、后果——就这五段
* 工具：GitHub 上搜 adr-tools（Nygard 自己写的命令行），或者直接 markdown 文档也行
* 学完找一份业内真实的 ADR 看：Thoughtworks Technology Radar 的 GitHub 仓库里有大量示例

3. Gartner 6R

* 这个没有"原文"，因为是 Gartner 咨询框架（要付费报告）
* 免费替代：AWS 的 Migration Hub 文档把它公开化了：aws.amazon.com/migration-hub → Prescriptive Guidance
* 6 个 R 就一张图的事，理解成本几乎为零
* 关键不是背 6 个 R 的定义，是学会用这个框架结构化讨论"哪些搬、哪些改、哪些扔"

### 一个更宏观的方向

如果你后面想系统学，这种"项目合并/系统改造"其实属于一个完整行业方向叫 Application Modernization（应用现代化）：

* 会议：QCon ArchSummit、ArchConf（Thoughtworks 主办）
* 报告源：Thoughtworks Technology Radar（每年两期，免费看）
* 行业玩家：Thoughtworks、Thoughtworks Technology Advisory、咨询公司里的 modernization practice
* 相关工具链：vFunction、CAST、Structure101（评估单体应用的拆分点）
* 但说实话，你不需要变成"应用现代化专家"。这个领域是给咨询公司和大企业架构组用的，对你这种全栈工程师，掌握 3~5 个模式够用十年。

## 我的实际建议

别"学完再干"，你手头的项目就是最好的教材。建议这样：

> 读 Fowler 那篇 + Nygard 那篇, 边合并项目边写第一份 ADR（你的"B→A 不 A→B"决策就是最好的第一份 ADR 素材）过程中遇到具体决策：查对应模式，缺啥补啥

## B->A 合并项目的路线规划

好，给你设计一个**4 周的项目驱动学习路线**，全程围绕你那个 B→A 合并项目展开。每周绑一个学习目标 + 一个项目实战任务，不脱节。

## 4 周路线总览

| 周次 | 学习目标 | 项目实战任务 | 产出物 |
|---|---|---|---|
| **W1 基础** | 读原文，建立概念 | 摸清两个项目现状 | 项目现状文档 |
| **W2 6R + ADR** | 用 6R 评估，写第一份 ADR | 拍板合并方向 | 6R 评估表 + ADR #001 |

## W1：基础概念 + 项目摸底

**学什么**

* 读 Martin Fowler 的 [StranglerFigApplication](https://martinfowler.com/bliki/StranglerFigApplication.html)（10 分钟）
* 读 Nygard 的 [Documenting Architecture Decisions](https://blog.cognitect.com/blog/2011/11/15/documenting-architecture-decisions)（10 分钟）
* 看 1 个真实案例：去 Thoughtworks Technology Radar GitHub 仓库搜 "strangler" 看 2~3 条

**项目实战**

* 把 A（v2/apps/web）和 B（v2/apps/workflow-dashboard）的代码各过一遍
* 重点摸清：数据模型（字段、关系）、核心流程（你描述的那几步）、对外接口
* 用你顺手的工具画一张「现状对比图」（哪怕是手画拍照都行）

**产出物**

* `docs/projects/merge-status.md` —— 两个项目现状对比，1~2 页够用

**检验标准**：能向别人 3 分钟讲清楚两个项目的核心差异

---

## W2：6R 评估 + 第一份 ADR

**学什么**

* 读 AWS Prescriptive Guidance 的 [6R 介绍](https://docs.aws.amazon.com/prescriptive-guidance/latest/strategy-acceleration/migrate-strategies.html)（20 分钟）
* 重点是 6R 的**使用方式**，不是定义本身——用一张表把项目功能分类

**项目实战**
* 列一份 A、B 项目的**功能模块清单**（颗粒度到"能独立交付"的级别，比如 A 的"策略匹配"、B 的"立项书生成"各算一项）
* 给每个模块打 6R 标签：Rehost / Replatform / Refactor / Repurchase / Retire / Retain
* 写 ADR #001：**「B→A 合并方向决策」**

**ADR #001 大致结构**

```markdown
# ADR-001: 合并 v2/apps/web 和 v2/apps/workflow-dashboard

## 状态
已接受

## 上下文
两个项目流程相似但数据结构不同，A 有 B 没有的策略层。

## 决策
B 迁移到 A，保留 A 的策略匹配/策略增强能力。

## 后果
- A 成为唯一数据源
- B 的 UI 渐进迁移
- 数据 schema 需统一

## 替代方案
- A→B（已否决）：成本高，破坏 A 成熟能力
- 共存（已否决）：维护成本翻倍
```

**产出物**

* `docs/projects/merge-6r-evaluation.md`
* `docs/adr/001-merge-direction.md`

**检验标准**：把这份 ADR 拿给任何一个工程师看，能在 5 分钟内说"哦我懂了为什么"

---

## W3：Strangler Fig 路径设计 + PoC

**学什么**

* 重读 Fowler 那篇的"如何识别绞杀点"段落
* 关键概念：**Anti-Corruption Layer（防腐层）**、**Branch by Abstraction**、**Parallel Run（并行运行）**
* 这三个是 Strangler Fig 的实操工具，必学

**项目实战**

* 设计合并路径：先合什么、后合什么、绞杀点放在哪一层
* **挑一个最小模块**做 PoC（建议从 B 的"立项书生成"切入——B 这块成熟，A 也有，迁移风险最低）
* PoC 至少跑通：旧 UI 调用 → 防腐层 → 新数据模型 → 旧数据落库

**产出物**

* `docs/projects/merge-strangler-path.md`（画个时序图/流程图）
* `docs/projects/poc-report.md`（PoC 跑通记录 + 踩坑记录）

**检验标准**：PoC 能在你本地跑起来，B 的某个 UI 走新数据模型正常工作

---

## W4：执行 + 复盘 + 第二份 ADR

**学什么**

* 边做边学：迁移过程中遇到的具体问题（数据迁移、接口兼容、状态机差异等）随时查相关模式
* 推荐加入书签：refactoring.guru、martinfowler.com、thoughtworks.com/insights（持续输入）

**项目实战**

* 真正完成一个完整模块的迁移（PoC 那个模块的完整版）
* 写 ADR #002：记录迁移过程中发现的**技术决策**（比如"为什么用双写而不是一次性切换数据"）
* 写一份个人复盘：**W1~W4 走下来，你对"项目合并"这件事的理解有什么变化**

**产出物**

* 可运行的合并代码
* `docs/adr/002-migration-xxx.md`
* `docs/personal/retro-merge-w1w4.md`（私人的，写给自己看）

**检验标准**：第二份 ADR 比第一份写得更快、更聚焦——说明你在内化方法
