# T2 - 从0到1稳定型新项目

**版本**：v1.0  
**更新日期**：2026-01-15  
**状态**：✅ 已配置

**定义**：**业务需求明确且稳定**（有完整的PRD、原型图和验收标准，需求变更率<10%），但采用**发布时间<1年的新技术栈/新框架**开发的项目，核心目标是**在可控的技术风险下，100%准确实现业务需求，按时交付高质量的稳定产品**。

## 适用边界

### ✅ 适用场景

- 业务需求已经过充分验证，不会有大的变更
- 必须使用新技术才能满足业务要求（如性能、跨端能力等）
- 团队有较强的技术学习能力和问题解决能力
- 项目周期3-6个月，有明确的上线时间要求
- 可以接受一定的技术风险，但不能接受业务失败

### ❌ 不适用场景

- 业务需求不明确或频繁变更的项目
- 涉及核心交易，资金安全或生命安全的关键系统
- 团队技术能力薄弱，没有新技术使用经验
- 没有任何缓冲时间，必须零风险交付的项目
- 可以使用成熟技术栈满足所有业务要求的项目

---

## 核心特点

- ✅ **业务需求明确**：有清晰的产品文档、原型和验收标准
- ✅ **技术栈全新**：使用最新的框架、库或技术（如React 19、Vue 4、Taro Next、Flutter 4等）
- ✅ **技术不确定性高**：文档不完善、社区不成熟、坑多、最佳实践未形成
- ✅ **技术验证周期短**：没有足够时间进行充分的技术预研
- ✅ **交付要求严格**：有明确的上线时间和质量要求
- ✅ **通常用于移动优先或跨端项目**：使用移动版本的框架+技术来做新项目

---

## 核心矛盾

**明确稳定的业务需求** vs **不确定不成熟的技术实现**

### Spec详细程度定义

| 等级 | 描述 |
|------|------|
| **无** | 仅列出验证点或目标，不写任何技术文档 |
| **轻量级** | 1-2页文档，包含核心数据模型字段和API接口定义 |
| **中等** | 每个核心功能模块1-2页文档，包含输入输出、主要流程和验收标准 |
| **详细** | 每个模块3-5页文档，包含完整的业务逻辑、边界条件和错误处理 |
| **极其详细** | 包含架构图、时序图、数据流图、完整的接口规范和技术规范 |

### 各阶段Human Gate审查重点

| 阶段 | 审查重点 |
|------|----------|
| 阶段一 | 技术验证是否全面，风险识别是否充分，备选方案是否可行 |
| 阶段二 | 架构是否合理，技术规范是否明确，接口定义是否完整 |
| 阶段三 | 基础框架是否稳定，通用组件是否好用，开发模式是否统一 |
| 阶段四 | 业务逻辑是否正确，代码是否符合规范，测试是否充分 |
| 阶段五 | 测试是否全面，上线方案是否完善，回滚预案是否可行 |

## 关键注意事项

1. **先技术验证，再架构设计，绝对不能跳过**：技术验证阶段必须覆盖所有核心技术点，任何一个点验证不通过都不能进入下一阶段

2. **业务层绝对Spec，技术层适当Vibe**：业务逻辑必须100%严格按照Spec实现，不允许任何"创新"；技术实现细节可以灵活探索，但最终必须统一

3. **建立实时更新的"踩坑知识库"**：所有遇到的技术问题、解决方案、临时workaround都要详细记录，团队全员共享

4. **在架构设计阶段就制定统一的技术规范**：包括编码规范、目录结构、命名规范、错误处理规范等，所有开发人员必须严格遵守

5. **预留30%-40%的技术缓冲时间**：新技术项目一定会遇到各种意想不到的问题，充足的缓冲时间是按时交付的关键

6. **适度封装，先能用再优化**：新技术下过度封装会导致问题更难排查；初期只做必要的封装，随着对技术理解的深入再逐步优化

7. **警惕AI对新技术的认知滞后**：AI的训练数据通常滞后3-6个月，对于发布时间<1年的新技术，AI生成的代码很可能过时或错误

8. **所有AI生成的代码必须人工核对官方文档**：不要相信AI关于新技术的任何"最佳实践"，必须以官方最新文档为准

9. **建立完善的回滚机制和应急预案**：所有上线操作必须有回滚预案；准备好"降级方案"，在新技术出现问题时可以快速切换到备用模式；**降级方案必须在技术验证阶段就开始设计，并在上线前完成完整测试**

10. **小步快跑，频繁验证**：不要等到所有功能都开发完再测试；每个小功能开发完成后立即测试，及时发现问题

11. **不要盲目追求新技术的所有特性**：只使用满足业务需求所必需的特性，避免使用过于复杂或实验性的特性

12. **定期进行技术分享和复盘**：每周进行一次技术分享，交流遇到的问题和解决方案；每两周进行一次项目复盘，及时调整开发策略

13. **一次只引入一个新技术**：如果项目需要多个新技术，先引入最核心的一个，稳定后再逐步引入其他；同时引入多个新技术会成倍增加风险和复杂度

### AI使用技巧

| 阶段 | AI使用策略 |
|------|------------|
| 技术验证 | 让AI生成多个可能的解决方案，然后人工验证哪个可行 |
| 架构设计 | 让AI提供架构建议，但最终决策必须由人类做出 |
| 基础框架搭建 | **不要让AI生成完整的基础框架代码**，应该让它生成代码片段，然后人工整合；AI生成的完整框架往往不符合团队的技术规范 |
| 业务开发 | 让AI根据Spec生成业务代码，人工审查后合并 |
| 问题解决 | 优先使用DeepSeek R1和Perplexity，它们更擅长解决新技术问题 |

## 典型风险与应对

| 风险类型 | 具体风险 | 应对措施 |
|----------|----------|----------|
| **技术风险** | 新技术有致命缺陷，无法满足核心需求 | 提前准备至少一个成熟的备选技术方案；技术验证阶段重点测试核心功能；设定明确的止损点 |
| **技术风险** | 遇到无法解决的技术问题，导致进度延期 | 建立多层次技术求助渠道：官方社区→付费支持→外部专家；预留30%-40%的缓冲时间；及时调整优先级，先开发不依赖该问题的功能 |
| **技术风险** | 新技术性能不达标，无法满足业务要求 | 提前进行性能测试；识别性能瓶颈，针对性优化；准备降级方案；必要时切换到备选技术方案 |
| **技术风险** | AI生成过时或错误的代码 | 所有AI生成的代码必须人工核对官方最新文档；不要相信AI关于新技术的任何"最佳实践"；优先使用官方示例代码 |
| **技术风险** | AI不知道新技术的已知bug和workaround | 开发前先搜索官方GitHub的issue列表；加入官方社区，了解最新动态；遇到问题先搜索是否是已知bug |
| **技术风险** | 技术债务快速积累 | 每个迭代预留20%时间清理技术债务；临时解决方案必须标注TODO，并明确重构时间 |
| **技术风险** | 新技术停止维护或被放弃 | 优先选择有大公司支持的新技术；关注GitHub星标增长和issue响应速度；提前准备迁移到成熟技术的方案 |
| **团队风险** | 团队成员技术水平参差不齐 | 先由技术骨干完成基础框架搭建和核心模块开发；建立结对编程制度；定期进行技术培训和分享 |
| **团队风险** | 学习曲线陡峭，开发效率低下 | 建立完善的开发脚手架和文档；封装通用组件和工具函数；避免团队成员同时学习多个新技术 |
| **项目风险** | 需求变更导致技术方案失效 | 严格控制需求变更；任何需求变更必须评估对技术方案的影响；预留需求变更缓冲时间 |
| **项目风险** | 上线后出现严重问题，无法快速修复 | 建立完善的监控告警系统；制定详细的上线和回滚预案；准备好技术支持团队，24小时待命 |

## 反模式与常见陷阱

> ❌ **绝对不要做的事情**：
>
> 1. 不要跳过技术验证阶段直接开始开发
> 2. 不要在没有明确架构设计的情况下就开始写业务代码
> 3. 不要盲目追求新技术的所有特性，只使用你真正需要的
> 4. 不要相信AI能解决所有新技术问题，AI的知识永远是滞后的
> 5. 不要过度封装，新技术下简单比优雅更重要
> 6. 不要同时引入多个新技术，一次只引入一个
> 7. 不要在生产环境中使用新技术的实验性特性
> 8. 不要没有回滚预案就上线
> 9. 不要把所有希望寄托在一个技术方案上，永远要有备选方案
> 10. 不要忽视技术债务，临时解决方案最终都会变成永久问题
> 11. **不要在新技术上进行业务创新**：业务需求已经是确定的，技术只需要准确实现业务即可，不要试图同时进行技术和业务双重创新
> 12. **不要为了使用新技术而改变业务需求**：技术是为业务服务的，不能因为技术限制而降低业务标准

## 各行业适配要点

### 软件互联网

- **高度契合**：新技术选型在互联网行业最活跃，技术验证阶段可以充分利用社区资源
- **适配重点**：优先选择社区活跃、文档完善的新技术；充分利用GitHub/Discord等社区支持
- **注意事项**：AI对新技术认知滞后的问题在互联网行业影响最小，可以较快获取最新信息

### 制造业

- **部分适用**：适合智能制造、工业4.0等新技术应用场景
- **适配重点**：技术验证需考虑车间环境（温度、湿度、电磁干扰）；工业协议兼容性是重点
- **注意事项**：制造业新技术采纳周期长，选型需考虑供应商长期支持能力；PLC/工控系统集成需特殊验证

### 医疗健康

- **有限适用**：仅适合医疗软件系统的新技术应用，如新一代HIS/EMR系统
- **适配重点**：医疗软件的新技术验证必须包含"安全性验证"；必须通过等保测评、FDA审查（如适用）
- **注意事项**：医疗软件的监管要求限制了新技术采纳速度；技术验证需预留合规审查时间

### 金融服务

- **高度契合**：金融科技领域是新技术应用的先锋，如区块链、AI风控等
- **适配重点**：新技术选型必须通过金融安全评估；涉及资金的新技术需额外风险评估
- **注意事项**：金融监管对新技术的态度趋于开放但仍严格；需关注央行/银保监会对新技术的监管要求

### 传统零售

- **有限适用**：仅适合零售数字化转型中的新技术应用，如智能推荐、数字孪生等
- **适配重点**：新技术必须能提升客户体验和销售转化；技术验证周期需配合零售节奏
- **注意事项**：零售行业对新技术投资回报敏感，验证周期不宜过长；新技术需考虑与现有POS/ERP系统集成
