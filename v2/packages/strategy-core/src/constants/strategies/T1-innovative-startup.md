# T1 - 从0到1创新型新项目

**版本**：v1.2  
**更新日期**：2026-01-15
**状态**：✅ 已配置

**定义**：完全基于新想法、新市场或新商业模式的独立项目，**业务需求高度不确定**，没有现有代码和业务基础，核心目标是**在最小成本下快速验证PMF（产品市场匹配）**。

## 适用边界

### ✅ 适用场景

- 全新产品，面向新用户群体
- 商业模式创新，没有可直接参考的成功案例
- 团队规模1-5人，项目周期6个月以内
- 失败成本可控，不会影响公司主营业务

### ❌ 不适用场景

- 基于现有业务的功能扩展或优化
- 有明确需求和验收标准的外包项目
- 涉及核心业务数据或资金安全的项目
- 团队规模超过5人的大型项目

---

## 核心特点

- 业务需求高度不确定，可能随时调整方向
- 允许试错，失败成本相对较低
- 速度优先于完美
- 需要快速迭代和用户反馈
- 技术栈通常选择成熟稳定的方案

### Spec详细程度定义

| 等级 | 描述 |
|------|------|
| **无** | 仅描述核心目标，不写任何技术文档 |
| **轻量级** | 1-2页文档，包含核心数据模型字段和API接口定义 |
| **中等** | 每个核心功能模块1-2页文档，包含输入输出、主要流程和验收标准 |
| **详细** | 每个模块3-5页文档，包含完整的业务逻辑、边界条件和错误处理 |

### 各阶段Human Gate审查重点

| 阶段 | 审查重点 |
|------|----------|
| 阶段一 | 是否验证了核心价值主张 |
| 阶段二 | 是否实现了MVP的核心功能，是否能正常运行 |
| 阶段三 | 业务逻辑是否正确，代码是否可维护 |
| 阶段四 | 架构是否可扩展，是否符合安全和性能要求 |

## 模块级开发模式配置

| 模块类型 | 推荐开发模式 | Human Gate等级 | 说明 |
|----------|-------------|----------------|------|
| **核心业务逻辑** | 随阶段变化 | L1→L3 | MVP阶段可Vibe，验证PMF后必须转为Spec；任何涉及资金和数据安全的部分全程Spec |
| **非核心业务逻辑** | 100% Vibe | L0→L1 | 如用户个人资料、设置等，快速实现即可 |
| **UI/UX界面** | 100% Vibe | L0→L1 | 快速迭代，允许AI自由发挥；阶段三后统一设计规范 |
| **数据模型** | 阶段三后转为100% Spec | L2→L3 | MVP阶段可用NoSQL允许灵活调整；阶段三后转为关系型数据库并固定Schema |
| **认证授权** | 阶段二后转为90% Spec | L2→L3 | MVP阶段可使用第三方认证（如Auth0）；阶段二后自行实现并严格审查 |
| **支付系统** | 100% Spec | L4 | 全程使用Spec模式，必须由资深开发者审查；优先使用成熟的第三方支付接口 |
| **数据统计分析** | 70% Vibe + 30% Spec | L1→L2 | 先快速实现核心指标统计；阶段三后完善数据模型和分析功能 |
| **后台管理系统** | 80% Vibe + 20% Spec | L1 | 优先使用低代码工具或AI快速生成；满足基本运营需求即可 |
| **消息推送/通知** | 70% Vibe + 30% Spec | L1 | 先实现基础功能；根据用户反馈逐步优化 |
| **第三方集成** | 90% Spec + 10% Vibe | L2 | 严格遵守第三方接口规范；重点处理错误和异常情况 |
| **内部工具/脚本** | 100% Vibe | L0 | 追求速度，不纠结代码质量；如果工具变得重要，再转为Spec模式 |

## 关键注意事项

1. **前期不追求代码质量，但要保证可理解性**：概念验证和MVP阶段，只要功能能跑就行，允许"脏代码"，但必须保留基本的注释和命名规范，避免AI生成的"天书代码"

2. **验证通过后必须增量重构，不是重写**：当核心价值得到验证后，不要一次性重写整个系统，而是分模块增量重构，每次重构一个小功能并验证

3. **定期清理技术债务，设定明确的重构节点**：每个迭代周期预留20%时间清理技术债务；MVP完成后和验证PMF后必须进行两次大的重构

4. **不要过早优化，也不要完全不优化**：在产品找到PMF之前，不要进行任何性能优化和架构优化，但要避免明显的技术错误和安全漏洞

5. **保留所有实验代码和用户反馈**：所有尝试过的方案都要保留，方便后续回溯和参考；所有用户反馈都要记录和分类，作为产品迭代的依据

6. **用户反馈优先于功能实现**：任何功能的开发都必须基于真实的用户反馈，不要凭想象添加功能

7. **严格控制MVP范围，避免过度工程**：MVP只保留验证核心价值所必需的功能，任何额外功能都放到后续迭代

8. **使用单体架构，不要过早引入微服务**：创新型项目初期应该使用简单的单体架构，微服务会增加复杂度和开发成本

9. **警惕AI幻觉，核心业务逻辑必须100%人工验证**：AI生成的代码可能包含隐藏的业务逻辑错误和安全漏洞，核心业务逻辑必须人工逐行审查，绝对不能完全依赖AI

10. **不要过度依赖AI，保持团队的技术能力**：AI是辅助工具，团队必须理解代码的工作原理，避免出现"AI写的代码没人能改"的情况

11. **建立每周发布机制，无论功能多少，每周至少发布一个版本**：快速迭代的核心是频繁发布，即使只有一个小的改进也要发布，保持用户和团队的节奏感

## 推荐工具链

### 通用工具链（所有阶段）

- **AI编码**：Cursor + Claude 3.5 Sonnet（主力）+ GPT-4o（备选）
- **Spec与文档管理**：Markdown + GitHub/GitLab + Notion
- **版本控制**：Git（使用feature分支工作流，小步频繁提交）
- **部署与托管**：Vercel/Netlify（前端）+ Supabase/Firebase（后端）+ Railway（全栈快速部署）
- **团队协作**：Slack + Notion + Figma

### 分阶段工具链

| 阶段 | 推荐工具 | 说明 |
|------|----------|------|
| **概念验证** | Figma AI + Midjourney（原型设计）<br>Cursor + Claude（快速编码）<br>Vercel（一键部署） | 追求速度，使用最简单的工具 |
| **MVP开发** | Supabase（数据库+认证）<br>Typeform（用户反馈）<br>Plausible（简单统计）<br>Sentry（错误监控） | 快速搭建完整的产品体系 |
| **产品打磨** | Hotjar（用户行为分析）<br>PostHog（产品分析）<br>GitHub Actions（CI/CD）<br>Jest（单元测试） | 完善数据统计和测试体系 |
| **规模化** | Datadog（全面监控）<br>AWS/GCP（云服务）<br>Docker（容器化）<br>Playwright（E2E测试） | 提升系统的稳定性和可扩展性 |

### AI使用技巧

| 阶段 | AI使用策略 |
|------|------------|
| 概念验证 | 让AI生成完整的原型，快速验证想法 |
| MVP开发 | 让AI生成单个功能的代码，人工审查后合并 |
| 产品打磨 | 让AI生成测试用例和文档，提高开发效率 |
| 规模化 | 让AI进行代码重构和优化，提升代码质量 |

> **通用技巧**：遇到不确定的问题，让AI提供至少3个不同的方案进行对比，不要只看第一个答案；要求AI解释每个方案的优缺点，再做决策

## 典型风险与应对

| 风险类型 | 具体风险 | 应对措施 |
|----------|----------|----------|
| **产品风险** | 方向错误，浪费时间和资金 | 每周进行一次产品评审；每2周发布一个版本；快速获取用户反馈；设定明确的止损点 |
| **产品风险** | 过度工程，MVP功能太多 | 严格定义MVP范围；使用"如果没有这个功能，产品就无法验证核心价值吗？"来判断每个功能是否必要 |
| **产品风险** | 用户反馈失真 | 与真实用户面对面交流；不要只看数据，要理解用户背后的需求；小范围灰度测试新功能 |
| **技术风险** | 技术债务爆炸 | 设定明确的重构节点；每个迭代预留20%时间清理技术债务；验证PMF后必须重构核心代码 |
| **技术风险** | 技术选型错误 | 优先选择成熟稳定的技术栈；避免使用过于前沿的技术；提前准备备选方案 |
| **技术风险** | AI生成代码有安全漏洞 | 所有涉及用户数据和资金的代码必须人工仔细审查；使用安全扫描工具（如Snyk）；不要让AI处理敏感信息 |
| **技术风险** | AI幻觉导致业务逻辑错误 | 核心业务逻辑必须人工验证；编写全面的测试用例；不要相信AI生成的"看起来正确"的代码 |
| **技术风险** | 过度依赖AI导致团队能力下降 | 要求团队成员理解所有核心代码；定期进行代码审查和技术分享；不要让AI做所有的决策 |
| **团队风险** | 团队burnout | 保持合理的工作节奏；不要追求完美；定期休息和复盘；庆祝小的成功 |
| **团队风险** | 核心成员流失导致项目停滞 | 代码全员共享；所有核心逻辑必须有文档；建立交叉培训制度；避免知识集中在单个人身上 |
| **商业风险** | 资金耗尽 | 严格控制成本；优先验证核心价值；设定明确的资金里程碑；提前准备融资计划 |
| **商业风险** | 竞争对手抄袭 | 快速迭代，建立用户壁垒；专注于用户体验和服务；不要过度依赖单一功能创新 |

## 反模式与常见陷阱

> ❌ **绝对不要做的事情**：
>
> 1. 不要在概念验证阶段就考虑规模化问题
> 2. 不要为了"代码优雅"而牺牲开发速度
> 3. 不要在没有用户反馈的情况下进行大规模重构
> 4. 不要同时尝试多个创新方向
> 5. 不要让技术决策主导产品决策
> 6. 不要相信AI能解决所有问题
> 7. 不要隐藏问题，遇到困难及时沟通和调整
> 8. 不要在MVP阶段就追求完美的用户体验
> 9. 不要为了融资而过度包装产品，添加不必要的功能
> 10. 不要忽视早期用户的负面反馈，它们往往比正面反馈更有价值

## 每周例会模板

1. **上周完成了什么**？（每人1分钟）
2. **这周计划做什么**？（每人1分钟）
3. **有什么阻碍**？（集体讨论解决方案）

```
## 轮流发言
```

## 各行业适配要点

### 软件互联网

- **高度契合**：快速迭代、小步快跑的模式与互联网产品开发天然匹配
- **适配重点**：充分利用AI辅助开发，追求极致开发速度；MVP范围可以更激进
- **注意事项**：避免过度追求代码质量；保持快速发布节奏；用户反馈循环至关重要

### 制造业

- **部分适用**：概念验证阶段可借鉴快速原型思路，但后续阶段需大幅调整
- **适配重点**：概念验证后需增加"工艺可行性验证"环节；MVP标准需考虑生产制造约束
- **注意事项**：制造业产品开发周期长、试错成本高，需在早期就引入生产部门评审；合规认证（安规/环保）需提前规划

### 医疗健康

- **慎重适用**：仅适合医疗信息管理、健康科技App等弱监管场景
- **适配重点**：即使在创新阶段，合规（如HIPAA/GDPR）也必须纳入考量；AI辅助开发需人工严格审查
- **注意事项**：医疗设备的软件开发必须采用T4或更高等级策略；任何涉及临床决策的功能必须全程Spec且通过监管审查

### 金融服务

- **有限适用**：适合金融科技App、支付创新等场景的初始验证
- **适配重点**：创新必须建立在安全合规基础上；涉及资金的MVP需全程高等级审查
- **注意事项**：反洗钱、数据隐私保护等合规要求必须在MVP阶段就考虑；金融监管沙盒的合规要求需提前了解

### 传统零售

- **高度契合**：零售创新通常围绕"消费场景"，MVP验证思路与互联网模式高度一致
- **适配重点**：快速响应市场促销/季节性需求；优先验证"能否带来销售增长"而非技术指标
- **注意事项**：零售行业季节性强，MVP验证需在旺季前完成；库存、供应链等核心系统需单独评估
